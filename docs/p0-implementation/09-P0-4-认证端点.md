## 1. 分层：策略在服务里，HTTP 只是翻译

```
AuthenticationController  (Spring，薄)      ← Cookie、CSRF、状态码
        ↓
AuthenticationService     (零依赖，厚)      ← 所有安全决策
        ↓
IdentityStore             (port)
        ↓
JdbcIdentityStore         (纯 java.sql)     ← 只调 V53/V55 函数，零表授权
        ↓
PostgreSQL                (V1–V55)
```

这么分是因为**安全策略散在控制器注解里就没法整体审查**。
"什么时候暴露信息、什么时候锁定、什么时候作废"全部在一个文件里读得完。

`JdbcIdentityStore` 只调函数、不写 SQL 逻辑，所以应用角色**不需要任何表授权**——
"Web 层能碰什么"是一份函数清单，而不是一次权限审计。

## 2. 贯穿全部端点的一条承诺

**调用方学不到"这个号码是否已注册"。**

| 场景 | 已注册 | 未注册 |
| --- | --- | --- |
| 申请验证码 | `202 ISSUED` | `202 ISSUED` |
| 验证码错误 | `401 ELMOS_AUTH_INVALID_CODE` | `401 ELMOS_AUTH_INVALID_CODE` |
| 重试窗口 | 相同 | 相同 |

**注册和登录是同一个端点**，客户端不能说自己想做哪个——因为"我要注册"这句话本身
就会泄露号码是否被占用。服务端在验证码通过**之后**才查账号是否存在，不存在就创建。

测试里把"已注册号码"和"未注册号码"的响应并排断言，就是为了防止以后有人
"为了体验好一点"把它们拆开。

一个例外是刻意的：**格式非法的号码返回不同答案**。这不泄露任何人的信息——
调用方本来就知道自己输了什么。

## 3. 刷新令牌盗用检测：端到端跑通了

上一阶段在 SQL 层验过，这一轮在服务层走了完整链路：

```
真实客户端                          攻击者
  ├─ 拿到 token#1
  ├─ 刷新 → token#2                 ├─ 早先复制了 token#1
  │                                 └─ 重放 token#1
  │                                      ↓
  │                                 REUSE_DETECTED
  │                                 整个会话作废
  └─ 用 token#2 刷新 → REJECTED  ←────────┘
```

最后一行是重点：**合法客户端也被登出了**。既然分不出谁是真身，就让双方重新登录。

`REUSE_DETECTED` 和 `REJECTED` 在协议上是两个不同答案——前者是安全事件，
后者只是一个过期的标签页。指标要分得开，前端也该告诉用户"为安全起见会话已结束"
而不是静默跳登录页。

## 4. 浏览器契约

刷新令牌**只出现在 Set-Cookie 里，永远不进 JSON**。即使页面上跑起了 XSS，也读不到它。

```java
public static final String REFRESH_COOKIE = "__Host-elmos_refresh";
```

`__Host-` 前缀不是装饰：浏览器只在 Secure + Path=/ + **无 Domain 属性**时才接受它，
这意味着**子域名（包括被攻击者拿下的那个）无法覆盖它**。这是它专门防的那个攻击。

CSRF 用双提交：CSRF cookie 刻意**可被脚本读**（这是双提交的前提——跨站页面读不到它），
和刷新令牌一起轮换。状态变更同时要求 SameSite 和双提交，因为两者单独都有已知缺口。

Cookie 标志有 6 条独立断言。**Cookie 属性是那种调试时被削弱、然后再没被恢复的东西**，
逐条点名的测试能让它在 review 里显形。

## 5. 组织切换每次重查成员资格

不信任会话里缓存的成员列表，每次切换都回库查。这样**被移除的成员立刻失去访问，
而不是等到下次登录**。

测试里验了三件事：能切进自己的组织、切不进别人的组织（返回 **404 而非 403**，
否则可以用来探测组织是否存在）、被停用后立刻切不进去。

## 6. 测试写错了，而 V53 的守卫抓到了

第一次写"被移除的成员无法切换"时，我直接停用了组织里唯一的 OWNER。
V53 的 `elmos_guard_last_owner` 触发器把它拦了下来：

```
ERROR: ELMOS_ORGANIZATION_LAST_OWNER_PROTECTED
```

**是测试写错了，不是代码。** 改成用一个非 OWNER 成员来测，
并且**顺手给守卫本身加了一条断言**——它是"误操作"和"没人能管理的组织"之间唯一的东西。
