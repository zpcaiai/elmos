## 1. V53 留下的四个口子

V53 建好了聚合，但跑起来的服务还缺四样东西：

| 缺口 | 后果 | V55 的补法 |
| --- | --- | --- |
| 刷新令牌只有一个哈希列 | 无法轮换，更无法发现被盗 | `authentication_token_generations` 追加表 |
| 没有投递记录 | "短信没收到"无法回答 | `identity_message_deliveries` 发件箱 |
| 没有持久化限流 | 进程内计数器发版即清零，多副本形同虚设 | `identity_rate_counters` + 固定窗口函数 |
| 开通与授权分两步 | 新用户注册完什么都跑不了 | `elmos_complete_signup()` 单事务完成 |

另外修了一处 V53 自己的问题：`accounts_password_shape` 写死 `ARGON2ID`，
而 **JDK 里没有 Argon2**——没装可选依赖的部署根本存不下密码。
V55 放开为 `ARGON2ID | PBKDF2_SHA256`，并把算法名连同哈希一起存，
将来加了 Argon2 依赖可以在下次登录时无感迁移。

## 2. 最值得看的一处：刷新令牌盗用检测

**只做轮换是不够的。** 攻击者复制了一个刷新令牌，如果合法客户端先轮换，
攻击者那份就直接失效——请求被拒，然后呢？我们什么都没学到，用户也不知道自己被偷过。

所以每一代令牌哈希都留下，并记录何时被取代：

```sql
-- 出示了一个已被取代的令牌 = 两方持有同一个秘密
IF v_generation.superseded_at IS NOT NULL THEN
    UPDATE authentication_sessions
       SET session_state = 'REVOKED', revocation_code = 'REFRESH_TOKEN_REUSED',
           compromised_at = now()
     WHERE ...;
    outcome := 'REUSED';
```

三种结果：`ROTATED`（正常）、`REUSED`（**整个会话作废**，不只是拒绝这一次）、`REJECTED`。

关键在于 `REUSED` 时**连合法客户端的新令牌也一起死掉**——这正是目的：
既然无法判断哪一方是真身，就让双方都重新登录。烟测里专门断言了这一条。

## 3. 枚举抵抗：失败必须长得一样

`elmos_consume_verification_challenge` 在**任何**失败下都返回 NULL：
目标不存在、验证码错、已过期、已用过、次数用尽——调用方分不出来。

如果"手机号未注册"和"验证码错误"能被区分，这个接口就是一台账号枚举机。
烟测里把这两条并排断言，就是为了防止以后有人"为了体验好一点"把它们拆开。

同样的原则在 `Secrets.constantTimeEquals`：`String.equals` 在第一个不同字符就返回，
通过时序泄露前缀匹配。对六位验证码，这足以把 10⁶ 次猜测降到大约 60 次。

## 4. 限流：三条独立的窗口

```
DESTINATION  / 60s   / 1 次    ← "重发"按钮不能变成对着一个号码的短信炮
DESTINATION  / 24h   / 10 次   ← 单号码的日花费上限
CLIENT_PREFIX/ 1h    / 30 次   ← 一个来源不能遍历号段
```

计数器落在数据库而不是进程内存里。**内存限流器在发版时清零、在多副本间不存在**——
而这恰恰是攻击者受益的时刻。客户端标识只取 /24 或前三组 IPv6，不存完整地址。

## 5. 境内短信的两条硬约束

`identity_message_providers` 的 CHECK：

```sql
CONSTRAINT identity_provider_active_shape CHECK (
    provider_state <> 'ACTIVE' OR (
        credential_reference IS NOT NULL
        AND (channel <> 'SMS' OR (signature_name IS NOT NULL AND filing_reference IS NOT NULL))
    )
)
```

**未报备的签名/模板发不了**——境内发未报备短信会导致整个签名被停，不是单条被拒。
所以缺 `signature_name` 或 `filing_reference` 时provider 无法变 ACTIVE。

第二条：**没有可用 provider 时拒绝签发验证码**。
发一个没人能送达的码，只会把用户困在一个等待输入的页面上。

（这也意味着**短信签名报备要第一天就提交**，通常有 3–5 个工作日审核期。）

## 6. 关掉我自己标过的那道接缝

第一轮我写过：「注册完必须立刻有额度，否则新用户看到的是
`ELMOS_EXECUTION_NO_ACTIVE_ENTITLEMENT`，而他完全看不懂。」

`elmos_complete_signup()` 把激活账号、开通组织、授予试用放进一个事务，
**并且在最后自己验一遍**：

```sql
IF elmos_execution_concurrency_limit(p_organization_id) < 1 THEN
    RAISE EXCEPTION 'ELMOS_SIGNUP_ENTITLEMENT_MISSING';
END IF;
```

不是相信调用顺序，是断言结果。烟测里也直接验了这一条。

顺带发现 V49 已经准备好了防滥用：`trial_grants.verified_subject_hash` 是**全局 UNIQUE**，
一个已验证身份只能拿一次试用。我的手机号 HMAC 正好直接喂给它——
烟测验证了同一个手机号无法开第二个试用组织。

## 7. Java 核心：57 项断言，抓到一个真实解析缺陷

零依赖，全部用 JDK。两个类：`Secrets`（OTP、令牌、HMAC、密码、常量时间比较）、
`Destinations`（手机号/邮箱归一化与掩码）。

**测试抓到的缺陷**：`user@@example.com` 被接受了。
`lastIndexOf('@')` 让本地部分变成 `user@`，而我只检查了长度和连续点——
**结果会是把验证码投递到一个用户根本没输入的地址**。已补上真正的字符集校验。

其余几条值得一提的断言：

- **OTP 均匀性**：采样 12 万次验证首位数字分布。
  `abs(random.nextInt()) % 1000000` 这个常见写法有约 2% 的偏斜（2³¹ 不是 10⁶ 的整数倍），
  白送攻击者猜测优势。测试用 5% 容差卡住它。
- **归一化是安全属性**：`13800138000`、`+86 138 0013 8000`、`008613800138000`
  必须坍缩成同一个 HMAC——否则同一个人开三个账号、拿三次试用，
  `trial_grants` 的唯一约束完全失效。有断言。
- **邮箱本地部分大小写敏感**（RFC 5321），只小写域名。折叠本地部分会把某些服务商
  视为不同人的两个邮箱合并成一个。
- **Pepper 缺失或过短直接拒绝**：短 pepper 比没有更糟，它看起来像保护。
- 密码：同一密码两次哈希必须不同（盐），篡改迭代次数不能让校验变便宜。
