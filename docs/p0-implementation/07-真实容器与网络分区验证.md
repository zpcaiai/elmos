# 真实 podman 与网络分区：两项验证的结果

> 复现：装 podman，导入测试镜像，`ELMOS_TEST_IMAGE=... ./build_and_test.sh`
> **Runner Agent 验收从 94 项增至 107 项**，其中 5 项跑在真实容器里。

上一轮标注"未验证"的五项里，有两项能在沙箱内真正做掉。做的过程中
**真实容器抓到一个必然在生产炸的缺陷**——这正是"真跑一次"和"读代码"的区别。

---

## 1. 真实 podman：抓到一个静默失败

### 1.1 第一次真跑的输出

装上 podman 4.9.3，本地构建一个带真实 manifest digest 的最小镜像，
用 **Agent 自己生成的那条完整命令**跑：

```
::elmos stage=building progress=10
uid=65532 gid=65532                                       ← 非 root 生效
network probe: 0                                          ← --network=none 真的没有路由
::elmos stage=packaging progress=90
/bin/workload: line 5: can't create /elmos/out/project.zip: Permission denied
run-exit=0                                                ← 而且退出码是 0
```

两条好消息、一个缺陷。缺陷是这样的：

- `JobWorkspace` 用 Agent 自己的身份创建 0700 目录；
- `ContainerRuntime` 里写死 `--user=65532:65532`；
- **两者之间没有任何东西把它们绑在一起**——能跑通只是因为部署时恰好一致。

更糟的是失败形态。`sh` 里重定向创建失败**不一定**置非零退出码，所以这个任务
**"成功"退出并且什么都没产出**。用户看到的是一个空下载和零错误信息。

（这条链路上唯一挡住它的是 `JobExecutor` 里那句
`WORKLOAD_PRODUCED_NO_ARTIFACT` —— 之前写它时只是觉得"成功却没产物不该算成功"，
现在证明它是承重的。）

### 1.2 修法：让它在启动时暴露，而不是在第一个客户任务上

三处改动：

**a. 工作负载 uid 变成显式配置**，默认取 Agent 自己的 uid：

```java
bounded(env, "ELMOS_RUNNER_WORKLOAD_UID", currentUid(), 1, 4294967)
```

`currentUid()` 在 Agent 是 root 时返回 65532 而不是 0——**工作负载永远不该是 root**，
所以 0 从来不是它的合法默认值。

**b. `JobWorkspace` 显式移交属主**，不再靠巧合：

```java
if (workloadUid != currentUid() || workloadGid != currentGid()) {
    for (Path directory : new Path[]{in, out, tmp}) {
        if (!WorkspaceAccessProbe.chown(directory, workloadUid, workloadGid)) {
            throw new IOException("WORKSPACE_OWNERSHIP_TRANSFER_FAILED");
        }
    }
}
```

工作区**根目录仍归 Agent**，只移交三个叶子目录——这样工作负载不能重命名或替换自己的工作区。

**c. 新增启动期 `WorkspaceAccessProbe`**：uid 一致就直接放行；不一致就真试一次 chown，
不成功**拒绝启动**并说清后果：

```
workload uid 69774 differs from the agent uid 65532 and ownership cannot be
transferred; the first artifact write would fail with Permission denied
```

探针是纯文件系统运算，不需要镜像，所以在注册之前跑，代价为零。

### 1.3 差点被我放过的假阳性

改完之后测试一次就绿了。但我之前手工跑同样的 uid 组合是失败的——不对劲。

查下来：测试里工作负载 uid 取到了 **0**，容器以 root 跑，所以写成功了。
**它通过的原因恰恰是绝对不该发生的情况。**

改成强制 65532 并加一条断言，重新验证：

```
after chown:  drwx------ 2 65532 65532 /tmp/ws3/out
uid=65532 gid=65532
network probe: 0
-rw-r--r-- 1 65532 65532 23 project.zip
generated-project-bytes
```

机制确认无疑：chown 是关键，非 root 写入成功，字节完全正确。

### 1.4 顺带两个部署级发现

**镜像 ID ≠ manifest digest。** `podman images --format {{.Id}}` 给的是 config digest；
`name@sha256:` 引用的是 **manifest digest**（`podman inspect --format {{.Digest}}`）。
用错会得到 `image not known`。给镜像 allowlist 填值时必须取后者。

**digest 引用默认会去 registry 拉。** 即使镜像在本地，`name@sha256:` 也会先 ping registry。
已在容器命令里加 `--pull=missing`，避免任务在租约中途卡在一次 registry 往返上。

### 1.5 真实容器端到端

最终 5 项断言跑在真 podman 上：

- [x] 工作负载以**非 root** uid 运行（显式断言 `workloadUid != 0`）
- [x] 真实 podman 任务成功
- [x] 真实容器产出了产物
- [x] 产物完成上传
- [x] **产物字节正是工作负载写的那些**
- [x] 真实工作区被拆除

## 2. 网络分区：自我围栏真的会自己触发

之前的"租约被夺"用的是显式 409。真实的分区不给 409——**控制面直接不回话**。
这条路径走的是 `HeartbeatPump` 里的时间判断，之前没有被覆盖过：

```java
long silentSeconds = Duration.between(lastSuccess, Instant.now()).toSeconds();
if (silentSeconds >= config.leaseSeconds() - SAFETY_MARGIN_SECONDS) {
    leaseLost.compareAndSet(null, "LEASE_RENEWAL_TIMED_OUT");
}
```

测试做法：任务开始跑 1.5 秒后**把假控制面整个关掉**，然后断言：

- [x] 被分区的 Agent 放弃自己的任务（`ABANDONED`）
- [x] **围栏发生在租约到期之前**（租约 30s、安全边界 10s，实测 < 30s）
- [x] 被分区的 Agent **什么都不上报**
- [x] 被分区的 Agent 仍然清理了工作区

第三条是最重要的：另一个 Runner 此刻可能已经拿到这个任务，一条迟到的
`SUCCEEDED` 会覆盖更新的事实。

## 3. 仍未验证的三项

照实标注，不含糊：

| 项 | 为什么这里做不了 | 怎么做 |
| --- | --- | --- |
| 真实 OSS | 需要凭据 | `OssSmokeTest` 一条命令，约 0.5 人日 |
| 真实 Spring 上下文 | 沙箱到 Maven Central 是 403 | 搬进模块后 `mvn test`，约 0.5 人日 |
| K8s 滚动更新零丢失 | 需要真实集群 | 灰度期观察一次发版，约 0.5 人日 |

另外，本轮的真实容器验证有一处环境差异要说明：沙箱里 podman 以 **root** 运行
（rootful），而生产是 **rootless**。`--userns=keep-id` 在两者下的映射语义不同，
所以「rootless 下 chown 是否可行」仍需在真实节点上确认一次。
不过启动期探针正是为此设计的——**不可行时它会拒绝启动，而不是产出空结果**。
