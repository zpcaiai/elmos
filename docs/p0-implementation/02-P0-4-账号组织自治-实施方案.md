# P0-4 实施方案：账号、组织与成员自治（境内 SaaS）

> 配套产物：`sql/V53__account_identity_and_organization_self_service.sql`（已在真实 schema 上验证）

---

## 1. 现状：租户身份完全外包给了 IdP

`apps/web-console/app/lib/server/accountSession.ts`：

```ts
const organizationId = typeof claims.organization_id === "string" ? claims.organization_id : ...;
const primary = membership(organizationId, roles, permissions);
```

租户、角色、权限**全部来自 IdP 的 token claims**。再加上 Spring 路径的 `ELMOS_TRUSTED_SINGLE_TENANT_ORGANIZATION_ID`，结论是：

- 没有企业 IdP 的客户**注册不进来**——而这正是境内自助 SaaS 的绝大多数目标客户；
- 产品内没有「创建组织」「邀请成员」「改角色」的任何入口；
- V9 建的 `user_identities` / `organization_memberships` / `authentication_sessions` 全是 `payload jsonb` 占位表——**建模了，但没设计**：没有邮箱字段、没有 user↔org 关联（`organization_memberships` 里根本没有用户列）、没有角色列。

---

## 2. 一个必须先讲清的模型问题

V9 的 `user_identities` 是 `organization_id NOT NULL`。这意味着：**人必须先属于某个组织才能存在**。

但真实世界是反的——人先注册，然后创建或加入组织，而且一个人可以同时属于多个组织（这在 ToB 里极其常见：顾问、外包、集团多子公司）。

所以 V53 引入唯一的新聚合 `accounts`，**刻意不做租户隔离**，并保留 V9 的表名做组织内投影：

```
accounts (全局，无 RLS)              ← 人。邮箱/手机/微信/密码/MFA
   │
   ├── account_credentials           ← 一个人的多种登录方式
   ├── account_sessions (= V9 authentication_sessions，已类型化)
   │
   └──< organization_memberships >── organizations     ← 谁在哪个组织、什么角色（RLS）
              │
              └── user_identities     ← 该组织内的 actor_id 投影（RLS）
```

`accounts` 无 RLS 的补偿：`REVOKE ALL FROM PUBLIC`，不含任何组织内容，且只经 `SECURITY DEFINER` 函数写入。

**`user_identities.actor_id` 是整个系统的枢纽**——现有的审计、证据、审批、任务记录全都以 actor_id 为主体。它在开通时生成一次、永不复用，所以被移除的成员不会继承前任的审计轨迹。

## 3. 境内登录设计

优先级按目标市场排：

| 方式 | 优先级 | 说明 |
| --- | --- | --- |
| **手机号 + 短信验证码** | P0 | 境内 SaaS 的事实标准。无密码首登即可用 |
| 邮箱 + 验证码 / 密码 | P0 | 团队协作场景仍以邮箱为主，邀请也走邮箱 |
| 微信扫码 | P1 | 降低注册摩擦；`account_credentials.provider = 'WECHAT'` |
| GitHub / Gitee OAuth | P1 | 目标用户是开发者，且顺带解决仓库授权 |
| 企业 OIDC / SAML | P2 | **可选项而非前提**，租户自助接入 + 域名验证 |

### 手机号的合规处理

手机号是《个人信息保护法》下的个人信息，不能明文躺在库里。V53 的做法：

```
phone_lookup_hmac  = HMAC-SHA256(KMS 里的 pepper, E.164)   ← 支持精确匹配登录
phone_last4        = '8888'                                 ← 支持人眼识别
phone_cipher_ref   = 信封加密后的密文引用                     ← 需要发短信时才解
```

pepper 存在 KMS，**不在数据库里**。这样一份数据库副本泄露也无法枚举手机号——拖库不等于拖走用户通讯录。

邮箱保持明文（投递和邀请匹配需要），但明确标注为个人信息，纳入导出与删除流程，且**禁止写入遥测与审计 metadata**（沿用 V50/V51 已有的隐私规则）。

## 4. 关键流程

### 4.1 注册 → 建组织（5 分钟内跑通，零运维介入）

```
输入手机号 → elmos_issue_verification_challenge（限流：同号 60s 一条、单日 10 条）
          → 短信下发（只存 code 的 SHA-256）
          → 校验 → accounts.status = ACTIVE, phone_verified_at = now()
          → elmos_provision_organization(org, name, account, actor, 'cn-north')
                ├─ organizations（复用 V9 的 ACTIVE / T1_SHARED_SAAS）
                ├─ organization_memberships（OWNER / ACTIVE）
                └─ user_identities（actor_id 生成）
          → elmos_grant_trial（V49 已有）→ 试用额度，并发上限 1
```

注意最后一步：**开通即授予试用订阅**。否则 `elmos_execution_concurrency_limit()` 返回 0，新用户注册完发现什么都跑不了。这是两个 P0 之间最容易漏掉的接缝。

### 4.2 邀请成员

```
OWNER/ADMIN 输入手机号或邮箱
  → organization_invitations（token 只存 SHA-256，7 天过期，同目标唯一 PENDING）
  → 发送链接
  → 受邀人注册/登录后 elmos_accept_organization_invitation(token_hash, account, actor)
  → membership + user_identities 落地
```

设计上的两个刻意选择：

- **邀请角色里没有 OWNER**。所有权转移走 `organization_lifecycle_requests` 的双向确认，不能靠发链接完成——链接会被转发。
- **列表里只显示掩码**（`138****8888`），完整目标只在投递那一刻使用。

### 4.3 角色模型

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| OWNER | 全部，含所有权转移、删除组织 | — |
| ADMIN | 成员、SSO、API Key、配额 | 转移所有权、删除组织 |
| MAINTAINER | 提交任务、连接仓库、审批 PR | 成员管理、账单 |
| MEMBER | 提交任务、查看结果 | 仓库连接、审批 |
| BILLING | 账单、发票、套餐 | 任何任务与代码 |
| VIEWER | 只读 | 一切写操作 |

`elmos_guard_last_owner()` 触发器保证组织永不失去最后一个 OWNER——这个转换在成员页、管理端、API、删除流程四个地方都可达，只有放在数据库里才拦得住。烟测已验证。

### 4.4 API Key

CI 里要调 ELMOS 就得有机器凭据。`organization_api_keys`：

- 明文只在创建时显示一次，库里只有 SHA-256；
- **强制过期，上限 366 天**（CHECK 约束，不是提醒）；
- 绑定具体 `actor_id`——任务、审计、证据继续只有一套 actor 词汇表；
- 前缀 `key_prefix` 用于界面识别和快速定位泄露来源。

## 5. 迁移路径

### M1 · 应用 V53（零行为变化）

新表建好，旧路径完全不受影响。IdP 登录继续工作。

### M2 · 回填现有租户

对每个已存在的 `organizations` 行：

```sql
-- 为每个已知 actor 建一个 account 并挂上 membership
INSERT INTO accounts (account_id, status, display_name, primary_email, email_verified_at) ...
INSERT INTO organization_memberships (..., account_ref, member_role, member_state, joined_at) ...
UPDATE user_identities SET account_ref = ..., actor_id = <既有 actor>, source = 'ENTERPRISE_SSO',
       provisioned_at = now() WHERE ...;
```

**关键**：`actor_id` 必须沿用既有值，否则历史审计、证据、审批记录会与新身份对不上。这是整个迁移里最容易造成不可逆损坏的一步，回填脚本必须先在快照上演练并逐条比对。

### M3 · 双通道登录

`accountSession.ts` 增加本地会话分支：

```ts
// 顺序：本地会话 → 企业 SSO（保留）
const principal = (await resolveLocalSession(request)) ?? (await resolveIdpSession(request));
```

组织不再从 claims 直接取，而是从 `organization_memberships` 查——claims 只用于**识别是谁**，不再用于**决定他属于哪**。这一步之后，IdP 从「租户来源」降级为「认证方式之一」。

### M4 · 上线自助注册与成员管理 UI

新增页面：`/signup`、`/onboarding`、`/settings/members`、`/settings/api-keys`、`/settings/sso`。

### M5 · 拆掉单租户后门

`ELMOS_TRUSTED_SINGLE_TENANT_ORGANIZATION_ID` 降级为仅本地开发（`NODE_ENV=production` 下拒绝启动）。Spring 代理改为按会话解析租户。

## 6. 验收标准

数据库层已验证：

- [x] 最后一个 OWNER 无法被降级或移除
- [x] 邀请令牌无法重放（第二次 `NOT_PENDING`）
- [x] 邀请接受后 membership + user_identities 同时落地
- [x] ACTIVE 账号必须有已验证的邮箱或手机
- [x] API Key 无法创建成永不过期
- [x] 新增的四张组织级表全部带 `tenant_isolation` 且 FORCE RLS

端到端还需要：

- [ ] 全新用户 5 分钟内完成：注册 → 建组织 → 拿到试用额度 → 邀请同事 → 同事看到同一工作区，**全程无运维介入**
- [ ] 同一个人同时属于两个组织，切换组织后只能看到对应数据（RLS 实测）
- [ ] 数据库快照泄露演练：证明无法从中还原任何手机号
- [ ] 账号注销：冷却期内可撤销，冷却期后数据按导出/删除流程处理
