## 1. 验证记录（不是纸上设计）

这三个迁移**不是写完就交**的。实际执行过程：

1. 在沙箱起了 PostgreSQL 16.13；
2. 按序应用了仓库里真实的 **V1–V51 全部 51 个迁移**（结果：1366 张表）；
3. 在其上应用 V52 / V53 / V54；
4. 跑 `smoke_test_p0.sql`，**27 条断言全部通过**。

过程中真实抓到并修复了一个缺陷：`elmos_claim_execution_jobs` 的 `RETURNS TABLE` 出参 `organization_id` 与表列同名，PL/pgSQL 报 `column reference "organization_id" is ambiguous`。这个错误只有真正执行才会暴露——静态审查看不出来。

复现命令：

```bash
./rebuild_and_test.sh    # 期望最后一行 P0 SMOKE TEST PASSED
```

> 注：仓库目标是 PostgreSQL 17.5，验证环境是 16.13。用到的特性（`FOR UPDATE ... SKIP LOCKED`、`make_interval`、`FILTER`、生成列外的所有语法）在两个版本上语义一致，但**上线前请在 17.5 上重跑一次**。

## 2. 三条路径的依赖关系

```
        ┌─────────────────────────────────────────┐
        │  P0-4 账号与组织自治 (V53)                │
        │  没有它 → 第二个用户注册不进来             │
        └──────────────┬──────────────────────────┘
                       │ 提供 organization / actor
                       ▼
        ┌─────────────────────────────────────────┐
        │  P0-1 Runner 集群与任务落库 (V52)         │
        │  没有它 → 一套部署只服务一个租户           │
        └──────────────┬──────────────────────────┘
                       │ 产出需要落地
                       ▼
        ┌─────────────────────────────────────────┐
        │  P0-3 对象存储 (V54)                     │
        │  没有它 → 多副本下载 404                  │
        └─────────────────────────────────────────┘
```

三者之间有两处容易漏的接缝，单独拎出来：

**接缝 A：注册完必须立刻有额度。**
`elmos_execution_concurrency_limit()` 在没有活跃订阅时返回 0（刻意的失败关闭）。所以 `elmos_provision_organization()` 之后必须紧接着调 V49 的 `elmos_grant_trial()`，否则新用户注册完发现什么都跑不了，而且错误信息是 `ELMOS_EXECUTION_NO_ACTIVE_ENTITLEMENT`——用户完全看不懂。

**接缝 B：产物发布依赖任务存在。**
`job_artifacts.job_id` 外键指向 `execution_jobs`。所以 V54 必须在 V52 之后应用，且 Runner 的产物上传要在任务仍处于非终态时完成。

## 3. 建议执行顺序

不建议三条并行全开——V53 的回填会动 `user_identities.actor_id`，而 V52 的任务记录以 actor_id 为主体。顺序如下：

| 阶段 | 内容 | 周期 | 出口条件 |
| --- | --- | --- | --- |
| **W1** | 应用 V52/V53/V54（零行为变化）+ 接入 CI；开始短信通道报备 | 1 周 | 三个迁移在 17.5 上通过；`make verify` 不受影响 |
| **W2–W3** | P0-4 的 M2 回填 + M3 双通道登录 | 2 周 | 现有租户能用新会话登录，历史 actor_id 一致 |
| **W3–W5** | P0-1 的 S1–S4（含 Runner Agent） | 3 周 | 两租户并发落在不同 Runner；Web 重启不丢任务 |
| **W5–W6** | P0-3 的 N2–N4 + P0-1 的 S5 | 2 周 | 3 副本下载一致；篡改被浏览器拒收 |
| **W6–W7** | P0-4 的 M4/M5 自助注册 UI + 拆单租户后门 | 2 周 | 陌生用户 5 分钟自助跑通全流程 |
| **W8** | P0-1 的 S6 删除旧路径 + 全量回归 | 1 周 | `scheduledJobs` 零命中 |

合计约 **8 周 / 80 人日**，两到三人可并行压缩到 6 周。P0-1 的 S4（Runner Agent，10 人日）是关键路径，建议 W1 就启动设计。

## 4. 这套设计守住的边界

仓库现有的工程纪律很强，方案刻意没有破坏任何一条：

| 既有原则 | 在本方案中的体现 |
| --- | --- |
| 控制面只裁决，不执行 | 控制面发租约、收报告；容器生命周期全在 Runner 侧 |
| 失败关闭 | 无订阅 → 并发 0；未验证 → 无法发布；未配置后端 → 拒绝而非降级到本地盘 |
| 终态不可改写 | 数据库触发器，不是代码约定 |
| 证据不可伪造 | 事件表仅追加；下载授权全部留痕 |
| 租户隔离 | 新增 14 张租户表全部 FORCE RLS；唯一两张例外表不含客户内容且已 REVOKE |
| 供应链不可变 | 运行镜像必须 `@sha256:`，正则 CHECK 兜底 |
| 隐私最小化 | 手机号 HMAC + 信封加密；无原始 IP / UA / 请求体 |
| 复用权威聚合 | 并发上限与保留期直接读 V49 套餐目录，不建第二处真相 |

## 5. 三个仍需你拍板的点

1. **计费单位到底是什么。** 目前 V49 的目录里有 token、credit、并发、保留期四个维度，但没有明确「一次生成 = 多少钱」。P0-1 的用量事件要挂在哪个维度上，直接决定 `execution_jobs` 完成时写什么计量记录。**这是唯一会反过来改数据模型的问题**，建议本周定。

2. **Runner 跑在哪。** 共享池（平台自有节点，`org-system` 持有）还是每租户专属？V52 两种都支持（`runner_pools` 按 org 归属），但决定了成本模型和 K8s 拓扑。境内 SaaS 首发建议共享池 + 严格 rootless 隔离。

3. **预览功能怎么办。** `generationRunner.ts` 的 `startRuntime`/`stopRuntime`（生成完一键启动看效果）是长驻进程，不是一次性任务。它不能继续留在 BFF 里，但也不适合直接套用当前的 job 模型。三个选项：建模为带 TTL 的独立 job kind、下沉到独立的预览服务、或者 v1 先砍掉。**这一项挡着 P0-1 的 S6**，需要在 W5 前定。
