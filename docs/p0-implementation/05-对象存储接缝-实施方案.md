## 1. 为什么手写 SigV4 而不是引 AWS SDK

先说清楚，因为这是本次唯一有争议的选择。

理由有三条：

1. **一套代码要同时服务 S3 和阿里云 OSS。** 目标市场是境内，主力后端是 OSS；开发和私有化用 MinIO。三者都讲 S3 协议，预签名的算法完全一致，用同一份实现比配三套 SDK profile 干净。
2. **只用到一个函数。** 控制面从不自己搬对象字节——它只签 URL、只做一次校验读。为一个函数引入一棵传递依赖树不划算。
3. **可以被硬验证。** 预签名是封闭的、有公开测试向量的算法。

第三条是决定性的：一个只"自洽"的签名实现毫无价值——它会跟自己一致，然后被服务端拒绝。所以
`SigV4PresignerTest` 把实现钉死在 AWS 文档的官方示例上：

```
  expected    aeeed9bbccd4d02ee5c0109b86d86835f995330da4c265957d157751f604d404
  actual      aeeed9bbccd4d02ee5c0109b86d86835f995330da4c265957d157751f604d404
  ok   presigned signature matches the published AWS vector
```

（bucket `examplebucket`、key `test.txt`、us-east-1、2013-05-24T00:00:00Z、86400 秒、
文档里的示例凭据。碰巧撞上一个指定的 64 位十六进制值是不可能的。）

**只实现了查询串（预签名 URL）这一种。** Header 签名没有半成品地放在那里——控制面不需要它，所以它不存在。

一个容易踩的坑，代码里有注释：**不能用 `URLEncoder`**。它把空格编成 `+`，把 `*`、`~` 处理成 AWS 不接受的形式，
结果是签名在本地自测通过、到线上被拒——最难查的那类 bug。测试里有五条断言专门守这个。

## 2. 三条失败关闭规则

### 2.1 未配置的后端拒绝一切，不降级到本地盘

```java
private void requireWritable() {
    if (!backend.writable()) {
        throw new ObjectStorageException("OBJECT_STORAGE_NOT_CONFIGURED");
    }
}
```

"先临时用本地盘顶一下"正是让多副本部署返回 404 的那个决定。V54 的 CHECK 已经保证
`LOCAL_FS` 永远无法变成 ACTIVE；这里再补一层运行时拒绝。

`READ_ONLY` 状态被单独区分：拒绝写、允许读。迁移或后端故障期间可以只停写不停读。

### 2.2 客户端声明的摘要永远不被信任

发布前控制面**把对象读回来重算 SHA-256**：

```
Runner 算 sha256 → 申请 presigned PUT → 直传 → 请求 publish
                                                    ↓
                                   服务端流式读回并复算 → 一致才 AVAILABLE
                                                    ↓
                                          不一致 → QUARANTINED（不是删除）
```

隔离而不是删除，是为了让事故仍然可查。

测试里跑了三种真实失败：

| 场景 | 结果 |
| --- | --- |
| 声明 26 字节、实际传 9 字节（截断上传） | `DIGEST_MISMATCH` 隔离，永不 AVAILABLE |
| 传了完全不同的字节（替换） | `DIGEST_MISMATCH` 隔离 |
| 根本没传 | `OBJECT_ABSENT` 隔离 |

这些都跑在一个真实 HTTP 假 S3 上，走完整的预签名 PUT → GET 回读链路。

### 2.3 加密头随 ticket 一起下发

```java
case "SSE_KMS" -> Map.of(
        "x-amz-server-side-encryption", "aws:kms",
        "x-amz-server-side-encryption-aws-kms-key-id", backend.cmkReference());
```

Runner 必须在 PUT 时回带这些头。这样 Runner **无法悄悄写出一个未加密的对象**——它拿不到"不加密"这个选项。

## 3. 租户隔离：不依赖应用正确性的那一层

对象键的第一段永远是租户：

```
oss://elmos-artifacts/<organization_id>/obj/<sha256>
```

文件名不进键（存在 `job_artifacts.filename`），所以同一份字节被两个任务以不同文件名发布时只存一份。

租户前缀的真正意义是：**即使应用层有 bug，bucket policy / RAM 策略也能再加一道边界**。
不依赖我们自己正确性的隔离，才是隔离。

`storageKey()` 对 organization_id 和摘要都做正则校验，`../org-b` 这样的穿越会被直接拒绝（有断言）。

还有一个刻意的取舍：**内容对象按租户唯一，不做全局去重**。全局按 digest 去重会把制品库变成
跨租户存在性预言机——租户 B 上传后系统秒回"已存在"，B 就知道 A 手里有字节相同的文件。
对做代码迁移的平台，这等于泄露"谁在用哪个框架的哪个版本"。省的那点存储不值这个。

## 4. 授权：不信任 Runner 声明的租户

两个 Runner 端点都**不读请求体里的 organization**：

```java
private String authorizeLease(String leaseId, String jobId, String leaseToken) {
    if (!storage.leaseOwnsJob(leaseId, jobId, sha256Hex(leaseToken))) {
        throw new LeaseRejected("ELMOS_LEASE_CREDENTIAL_MISMATCH");
    }
    return storage.organizationForLease(leaseId)      // ← 租户从租约记录读出
            .orElseThrow(() -> new LeaseRejected("ELMOS_LEASE_UNKNOWN"));
}
```

`leaseOwnsJob` 同时校验：租约 ID、任务 ID、令牌哈希、租约状态在 `ISSUED/ACTIVE`、且未过期。
猜到别人租约 ID 的 Runner 过不了令牌校验；伪造 organization 的 Runner 会被忽略。

租户侧的下载端点用会话身份，**任务不存在时返回 404 而不是 403**——否则一个租户可以拿它来探测
另一个租户的任务是否存在。

## 5. 下载：presigned URL + 浏览器复算

TTL 300 秒，数据库 CHECK 兜到 900 秒上限（`artifact_grant_max_ttl`），适配器再拒一次超过 15 分钟的请求。
presigned URL 是不记名凭据，三处都卡是刻意的。

前端**一行不用改**：现有的浏览器端 SHA-256 复算逻辑本来就是对的，而它正是把不记名 URL 变安全的原因——
即使链接被中间人替换，摘要不符就会被拒收。所以 ticket 里同时返回 `contentSha256` 和 `byteSize`。

每发一个 URL 就写一行 `artifact_download_grants`（谁、何时、哪个产物、几次、何时过期），
**URL 和签名本身不入库**。"上周谁下载了客户的代码归档"因此是可回答的。

## 8. 一个仍然敞开的口子

当前实现是**单次 PUT**，`max_object_bytes` 默认 5 GB。S3 协议单次 PUT 的硬上限也是 5 GB，
超过必须走 multipart upload。整库转换的 Evidence Pack 有可能超过这个尺寸。

我没有实现 multipart，因为它会把这个模块的复杂度翻倍（分片预签名、并发上传、完成/中止、
孤儿分片清理），而现在还不知道产物尺寸的真实分布。**建议先上线并统计 `content_objects.byte_size`
的 P99**，超过 2 GB 再实现。届时 `ArtifactPublisher` 已有 `ARTIFACT_TOO_LARGE` 失败关闭，
不会静默截断。
