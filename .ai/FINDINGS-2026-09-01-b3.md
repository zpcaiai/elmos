## 4. 上游 sqlglot 缺陷 —— 6 个可上报项，各带最小复现

每一项都是在 `sqlglot==30.14.0` 上**实跑**的，`PARSED` / `REJECTED` 是记录的返回，不是推断。

### U-1 （家族 A，17 条）`LANGUAGE sql` + `SECURITY DEFINER` 在 postgres 方言下解析失败

```python
import sqlglot
sqlglot.parse_one(
    "CREATE FUNCTION f() RETURNS void LANGUAGE sql SECURITY DEFINER AS $$ SELECT 1 $$",
    read="postgres")
# ParseError: Required keyword: 'this' missing for
#             <class 'sqlglot.expressions.properties.LanguageProperty'>. Line 1, Col: 5.
```

**期望**：解析为 `Create`，属性含 `LanguageProperty(this=sql)` 与 `SqlSecurityProperty(DEFINER)`。

**已实测的行为矩阵**（这是定位根因的关键，建议原样贴进 issue）：

| 写法 | 结果 |
| --- | --- |
| `LANGUAGE sql SECURITY DEFINER` | **REJECTED** |
| `LANGUAGE sql SECURITY INVOKER` | **REJECTED** |
| `LANGUAGE SQL SECURITY DEFINER`（大写） | **REJECTED** |
| `LANGUAGE plpgsql SECURITY DEFINER` | PARSED |
| `LANGUAGE c SECURITY DEFINER` | PARSED |
| `LANGUAGE "sql" SECURITY DEFINER`（加引号） | PARSED |
| `SECURITY DEFINER LANGUAGE sql`（换序） | PARSED |
| `LANGUAGE sql IMMUTABLE` / `STRICT` / 单独 | PARSED |

**根因判断**：只有语言名恰好是裸标识符 `sql` 时才失败，加引号或换序即可。
这与 MySQL 的 `SQL SECURITY DEFINER` 属性形状撞车 —— 解析器在 postgres 方言下
仍然把 `sql SECURITY DEFINER` 匹配成了 `SqlSecurityProperty`，
于是 `LanguageProperty` 拿不到它的 `this`。错误信息里 `LanguageProperty` 缺 `this` 正好印证。
`LANGUAGE "sql"` 能过（引号让它不再是那个关键字 token）是最强的旁证。

**影响面**：本仓库 17 条，全部是 `V59` / `V74` / `V77` 里的
`CREATE OR REPLACE FUNCTION ... LANGUAGE sql SECURITY DEFINER SET search_path = ...`。

### U-2 （家族 I，3 条）MySQL 存储过程的 `IN` / `OUT` / `INOUT` 参数模式

```python
sqlglot.parse_one("CREATE PROCEDURE p(IN a INT) BEGIN SELECT 1; END", read="mysql")
# ParseError: Expecting ). Line 1, Col: 23.
```

| 写法 | 结果 |
| --- | --- |
| `p(IN a INT)` / `p(OUT a INT)` / `p(INOUT a INT)` | **REJECTED** |
| `p(a INT)`（无模式） | PARSED |
| `p()` | PARSED |

**期望**：解析为 `Create`，参数带模式。
**影响**：`sakila-mysql.sql` 的 `rewards_report`(446)、`film_in_stock`(558)、`film_not_in_stock`(574)。

### U-3 （家族 I，2 条）MySQL routine 体内**两条及以上** `DECLARE`

```python
sqlglot.parse_one(
    "CREATE FUNCTION f() RETURNS INT BEGIN DECLARE a INT; DECLARE b INT; RETURN a; END",
    read="mysql")
# ParseError: Invalid expression / Unexpected token. Line 1, Col: 66.
```

| 写法 | 结果 |
| --- | --- |
| `BEGIN DECLARE a INT; RETURN a; END`（1 条 DECLARE） | PARSED |
| `BEGIN DECLARE a INT; DECLARE b INT; RETURN a; END`（2 条） | **REJECTED** |
| `BEGIN DECLARE a INT; DECLARE b INT; DECLARE c INT; ... END`（3 条） | **REJECTED** |
| `BEGIN DECLARE a INT; SELECT COUNT(*) INTO a FROM t; RETURN a; END` | PARSED |
| `BEGIN DECLARE a INT; DECLARE b INT; SELECT ... INTO a ...; END` | **REJECTED** |

**附带的第二个面**（同一根因很可能）：单条 `DECLARE` 后跟一个**非原子** `RETURN` 也失败 ——

| 写法 | 结果 |
| --- | --- |
| `DECLARE v INT; RETURN v;` | PARSED |
| `DECLARE v INT; RETURN NULL;` / `RETURN TRUE;` / `RETURN (1);` | PARSED |
| `DECLARE v INT; RETURN 1;` | **REJECTED** |
| `DECLARE v INT; RETURN v+1;` | **REJECTED** |

**期望**：MySQL 允许一个 `BEGIN ... END` 体内任意多条 `DECLARE`；应全部解析。
**影响**：`get_customer_balance`(513)、`inventory_in_stock`(608)。

### U-4 （家族 I，1 条）MySQL `DECLARE ... HANDLER`

```python
sqlglot.parse_one(
    "CREATE FUNCTION f() RETURNS INT BEGIN "
    "DECLARE EXIT HANDLER FOR NOT FOUND RETURN NULL; RETURN 1; END", read="mysql")
# ParseError: Invalid expression / Unexpected token. Line 1, Col: 94.
```

**实测确证**：把 `inventory_held_by_customer`(590) 原文里那一行 `DECLARE EXIT HANDLER ...` 删掉，
**同一个 routine 立刻 PARSED（`Block`）** —— 所以它是该语句的唯一阻塞点。

### U-5 （家族 D，2 条）`CREATE FUNCTION` 的**无名参数**不支持多词 / 带参类型

```python
sqlglot.parse_one(
    "CREATE FUNCTION public.last_day(timestamp with time zone) "
    "RETURNS date LANGUAGE sql AS $_$ SELECT 1 $_$", read="postgres")
# ParseError: Expecting (. Line 1, Col: 51.
```

| 写法 | 结果 |
| --- | --- |
| `f(timestamp with time zone)` / `f(timestamp without time zone)` | **REJECTED** |
| `f(numeric(4,2))`（无名 + 带参类型） | **REJECTED** |
| `f(p timestamp with time zone)`（给参数起个名） | PARSED |
| `f(character varying)` / `f(double precision)`（无名多词） | PARSED |
| `f(integer)` / `f(timestamptz)` | PARSED |

**期望**：PostgreSQL 的函数参数名可省略，`timestamp with time zone` 与 `numeric(4,2)`
都是合法的无名参数类型，应解析。
**影响**：`pagila-postgres.sql`(217)、`sakila-postgres.sql`(767) —— 就是 08-25 那份报告里
点名的 pagila / sakila 两个"一句话毁掉整个文件"的构造。

## 6. 我们可以前置规避的 —— 3 项，方案与实测

这三项的价值是**归因正确**，不是覆盖率。现在它们被算进
`CERTIFIED_DDL_PARSE_FAILED`，等于把客户端构造和我们自己的切分缺陷赖到方言语法上——
这正是 08-25 那轮已经吃过一次亏的错法（`\c chinook;` 当时毁掉了 586 KB）。

**以下是建议，本轮没有落盘。**

### R-1 （C，2 条）反斜杠 psql 指令按换行终止

`statement_splitter.split_statements` 只在顶层 `;` 上切。
`\set ON_ERROR_STOP on` 没有分号，于是和后面的 `BEGIN;` 粘成一个 chunk；
又因为该 chunk 以 `--` 注释开头，`scan.py` 里
`raw.text.lstrip().startswith("\\")` 的客户端指令判定也没命中，最终报成 PARSE_FAILED。

**两个独立的小问题，都要改**：
1. `split_statements`：行首的 `\` 指令按**换行**终止，单独成一条 `RawStatement`。
2. 客户端指令判定：应在**剥掉前导注释之后**再判断是否以 `\` 开头。

**实测**：剥掉前导注释与空白后，两条 `\set ON_ERROR_STOP on` 都能正确切出，
应归 `CERTIFIED_DDL_CLIENT_DIRECTIVE`；剩余部分 `BEGIN` 归
`CERTIFIED_DDL_UNSUPPORTED_STATEMENT`。覆盖率不变。

### R-2 （G，9 条）MySQL `source` 客户端指令

`source load_departments.dump` 之类 9 条，是 mysql CLI 指令，和 psql 的 `\i` 同性质，
永远不会发到服务器。现在被当成 SQL 解析失败。

**建议**：把 `CERTIFIED_DDL_CLIENT_DIRECTIVE` 的识别从"以 `\` 开头"扩展到也认
MySQL 方言下行首的 `source <path>` / `\. <path>`。实测有 9 条精确匹配 `^source\s+\S+$`。
**注意**：这个识别必须**限定在 mysql 方言**——别的方言里 `source` 可以是普通标识符。

### R-3 （I，3 条）切分器认 `DELIMITER`

不认 `DELIMITER //` 会把一个 routine 体切成碎片，产生 3 条**假**的 PARSE_FAILED
（`DECLARE last_month_end DATE`、`SELECT ... INTO count_rewardees`、`END //`）。

**实测（这一条务必照抄进任何后续决策）**：写了一个认 `DELIMITER` 的切分器重切
`sakila-mysql.sql`，9 条 finding 还原成 6 条真实 routine，
**然后这 6 条被同一个 pinned parser 逐条重解析，6 条全部仍然 REJECTED**（根因即 U-2/U-3/U-4）。

所以 R-3 的收益是：`sakila-mysql.sql` 的 PARSE_FAILED 从 9 条降到 6 条，
且那 6 条的原因码变成可上报的真缺陷。**进入子集的语句：0 条。**

（附带观察，未展开：DELIMITER-aware 切分下，`ins_film` / `upd_film` / `del_film`
三个 trigger 是 PARSED 的，它们本来就不在这 44 条里，此处仅作为切分器正确性的旁证。）

- **没有向上游提交 issue。** U-1..U-6 只是备好了最小复现，未上报，未检索
  sqlglot 是否已有重复 issue，也**未在 30.14.0 之外的任何版本上验证**——

**明确没验：**

- **75.78% 这个覆盖率没有独立验证**，也没有做 B2 要求的四引擎零回归对比。
  它同时含语料变化与引擎变化两个变量，**不可作为 B 线成绩引用**。
- **所有"能过 / 不能过"的结论都只是 sqlglot 解析腿。** 本轮**一次真库都没跑**
  （无 PG16 / MySQL8 DSN）。仓库已记载真跑时 971 条里 200+ 条真服务器不接受，
  所以 §4 的"期望行为"是**期望 sqlglot 能解析**，不等于该语句在目标库上能执行。
  U-6c（`VARCHAR(40) BINARY`）、家族 E（`VIRTUAL`）尤其要小心。
- **没有验证发射侧。** 44 条全部卡在源侧解析，从未走到目标方言发射与重解析，
  所以就算解析通了，发射侧会不会拒绝 `NOT_PROBED`。
