## 2. C1 那一环到底是解析器还是正则（这是这条线最该被追问的一点）

**照实说：Python 是解析器，其余语言是正则，两者在输出里已经分得开。**

实测（`_to_delete/c5-demo/flows.json` 与 `graph.json` 是真返回，不是我编的）：

```
[2] elmos-flow-discovery: state=PARTIAL_LOCAL_EXECUTED  code=STATIC_FLOW_CANDIDATES_DISCOVERED
    import-flows=57   control-flow nodes=79 edges=99   origin=PARSED   parse_status=PASSED
    import-flow origins: ['PARSED']      import-flow confidence: ['INFERRED']
[4] elmos-project-intelligence-graph: files=13 symbols=320
    symbol-origins={'PARSED': 320}   import-edges=57   edge-origins={'PARSED': 57}
```

### 2.1 「解析器给出的」与「推断的」已经是两个独立字段

C1 验收要求「现有的 `confidence: INFERRED` 必须换成解析器给出的与推断的两种明确来源」。
树上的做法是**加了一个正交的 `origin` 字段**，而不是改 `confidence` 的取值：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `origin` | `PARSED` / `REGEX` | **这条事实是谁读出来的**：`ast` 还是逐行正则 |
| `confidence` | `INFERRED` / … | **这条事实能推出多少**：import 边被解析器精确读到，但「有 import」≠「控制流真的走过去」 |

我认为这个拆法是对的，而且比 backlog 原文的要求更准：一条 import 边可以同时是
`origin=PARSED`（解析器读到的，不是猜的）和 `confidence=INFERRED`（它证明不了运行时路径）。
`discover_flows` 的 docstring 里把这件事写明了。

### 2.2 但 C1 只做完了一半，别当成 DONE

- **只有 Python 有解析器。** `python_structure.py` 只处理 `.py/.pyi`；其他一切走
  `_regex_symbols` / `_regex_imports`，标 `origin=REGEX`。backlog C1 写的是
  「先做 1–2 门语言（建议 Python + Java）」，**Java 没做**。
- **`derive_data_lineage` 和 `reconcile_api_event_topology` 仍然是纯正则**
  （`domain.py` 里 `re.compile(r"(?i)\b(?:from|join|into|update)\s+…")` 原样在），
  且它们的输出**没有 `origin` 字段**——也就是说这两条线上「解析器给的」与「猜的」**仍然混着**。
- 所以准确的说法是：**C5 这条链路上喂进来的图，控制流与模块结构是解析器给的；
  数据血缘与 API 拓扑还是正则投影。** 我的演示没有用后两者。

## 4. 抓到的缺陷

### 4.1 ⚠️ 渲染端标签白名单把判定条件抹平成同一个词 —— **没修，需要拍板**

**症状（真产物里的，不是推断）**：

```
spec 里的判定标签            渲染进 SVG / PPTX 之后
"ch == '['"          ─┐
"ch == ']'"          ─┼──►   "ch"        ← 三个不同分支，图上一模一样
"ch == '\\'"         ─┘
"while i < n"                "while i n"
"rest.startswith(':') or rest.startswith('=') or …"
                             "rest.startswith( ) or rest.startswith( ) or …"
```

量化：**20 个判定标签只有 3 个原样活下来（15%）**；79 个节点标签只有 35 个（44%）没被改动；
19 个互不相同的源判定渲染后只剩 17 个不同的字符串——其中 1 组碰撞（`in_class`）是源码本身
就有两处相同条件，**另 1 组（3 个判定 → `ch`）是渲染器造成的**。

**根因**：`diagram_layout.sanitize_label` 的字符白名单是 `字母数字 + " _-.,()"`，
其余一律换成空格。它和 Mermaid 渲染器的 `domain._safe_mermaid_label` **被一条测试逐字节钉在一起**
（`test_sanitizer_is_byte_identical_to_the_mermaid_sanitizer`）。

**为什么这次才炸**：这个白名单对「组件名」是够用的（`refund-api`、`j2p.emit.python` 都活得下来），
`FINDINGS-2026-09-01-c2-c3.md` §8 也提过标点会丢。**但控制流标签的主体就是运算符**
（`==`、`<`、`>=`、`[]`、引号），所以同一条规则在流程图上是毁灭性的，在组件图上几乎无害。
C2 那轮画的是组件图，所以没暴露。

**为什么我没改**：这是安全边界，不是排版参数。C2 的结论原文是「要放宽必须动那个安全边界，
我没有替你做」。我同意，并且补一条技术判断供拍板：

- Mermaid 那侧白名单是**唯一**防线，因为 Mermaid 的标签会被再解析一次，标签能逃出图形语法；
- SVG / PPTX 那侧还有**第二道独立防线**——XML 转义（`test_injection_in_a_label_cannot_escape_the_svg`
  与 `test_xml_escaper_neutralises_markup_on_unsanitized_input` 都在守它）。
- 所以「给导出端放宽字符集、保留 XML 转义」在技术上站得住，**但它会拆掉那条把两个 sanitizer
  钉死的测试**，而那条测试是故意加的（防止两个渲染器分叉）。**这是一个决定，不是一个补丁。**

**在拍板之前，演示时请避开表达式密集的函数**，或者接受「判定框只显示变量名」。

### 4.2 `generate_presentation` 只认 `from/to`，喂 canonical 边就产出 `None -> None` —— **已修**

**症状**：C5 这条链路里，同一份边同时喂给 `elmos-diagram-spec-engine` 和
`elmos-presentation-generation`。前者从一开始就同时接受 `from/to` 与 canonical 的
`source/target`（`domain.py` 里 `has_canonical_endpoints` 那段），后者只读 `from/to`。
结果是 **PPTX 的 Relationships 这一页整页 `None -> None`，而 handler 仍然报成功**。

真实产物截图（修之前，LibreOffice 转 PDF 后 `pdftotext` 抽的第 3 页）：

```
Relationships
None - None
None - None
...   (八行)
```

**修法**：`f"{edge.get('source', edge.get('from'))} -> {edge.get('target', edge.get('to'))}"`。
输出键元组没动（仍是 `("digest","pptx_generated","slides")`），`pptx_generated` 仍被
`_AUTHORITY_FALSE_PATHS` 钉死为 False，有测试守着这条边界。修后同一页：

```
Relationships
j2p.cli - j2p
j2p.cli - j2p.diff.harness
j2p.cli - j2p.emit.python
...
```

（`->` 在图上显示成 `-` 是 §4.1 那条白名单干的，不是这次修的范围。）

### 4.3 同一个缺陷还在另外两个 handler 里 —— **只报告，没改**

同一套「只认 `from/to`」的读法还出现在两处，**都真实探过，不是读代码推的**：

```
--- 喂 canonical source/target ---
  elmos-presentation-generation      : ['a -> b']              ← 已修
  elmos-architecture-documentation   : ['- None -> None (imports)']
  elmos-impact-analysis  (b 变更)     : impacted=['b']          ← 漏了 a
--- 喂 legacy from/to ---
  elmos-presentation-generation      : ['a -> b']
  elmos-architecture-documentation   : ['- a -> b (imports)']
  elmos-impact-analysis  (b 变更)     : impacted=['a', 'b']
```

- `elmos-architecture-documentation`（`generate_document`，`domain.py:1694`）：
  和 4.2 同一形状，一行可修。
- **`elmos-impact-analysis`（`analyze_impact`，`domain.py:1877`）是三个里最危险的**：
  它不是打印错，是**沉默的假阴性**——喂 canonical 边时，「改了 b，谁受影响」答成「只有 b」，
  漏掉了 import 它的 a。影响分析报「没有别的受影响」比报错更坏。

  **没改的理由**：不在 C5 链路上，各自需要自己的测试与反事实对照；而且
  `analyze_impact` 的修法要顺带决定「反向索引该按哪套词汇建」，那不是我该替谁定的。
  **建议单开一条**，两处一起改，一起补测试。

### 4.4 `match` 语句被整块折叠成一个框（分支一个都不画，也不说）—— **已修**

`ast.Match` 不在 `flowgraph._STRUCTURED` 里，`ast.TryStar`（`except*`）也不在。
后果是：一个五路 `match` 在图上是**一个 process 方框**，四个分支既没画出来，
**也没有任何 diagnostic 说它们被吞了**——这正是「分支缺一个」的定义。

- 现状是**潜伏**而不是正在发生：全仓 `grep` 过，`engines/` 与 `packages/` 下
  **零处 `match` 语句、零处 `except*`**。但引擎自己要求 Python ≥ 3.12，写出来只是时间问题。
- **修法**：`match` 画成**一条链**（不是扇形），每个 case 一个判定节点，
  `true` 进 case body、`false` 进下一个 case——因为 `match` 的语义就是「前面都没匹配才试这个」；
  guard 进标签（`case [x, y] if x > y`），否则同 pattern 不同 guard 的两个分支画出来一模一样。
  `except*` 与 `except` 同形，直接并入 `_try`。
- 实测：

  ```
  node kinds: {'start':1,'end':1,'merge':4,'decision':5,'process':9,'loop':1}
  decision labels:  match value case 0
                    match value case [x, y] if x > y
                    match value case {'kind': k}
                    match value case _
  ```

### 4.5 同名函数被静默挑一个 —— **已修（改成会说话，选择行为没动）**

`function_control_flow` 按名字找函数（`ast.walk` 的第一个命中）。实测被分析对象里
**26 个文件里有 7 个存在同名函数，共 59 个重名**，最极端的是
`runtime/j2p_runtime.py` 里 **13 个 `__init__`**。也就是说「给我画一下 `__init__` 的流程图」
会拿到十三分之一，**而且没有任何提示**。

**修法是最小的**：**选择行为一个字没动**（仍是 `ast.walk` 的第一个），只在重名时往
已有的 `diagnostics` 列表里加一条：

```
2 definitions named run at lines 3, 7; drew the one at line 3
```

`diagnostics` 本来就已经通过 `discover_flows` 透传出来，`_OUTPUT_KEYS` 里
`elmos-flow-discovery` 钉的是 `("flows","unknown_runtime_branches")` 两个顶层键，没有被加宽。

### 4.6 编译出来的 Diagram Spec 丢掉 `title`，所以每张图都叫 "Diagram" —— **已修**

`layout_diagram` 会读 `spec["title"]`，HTML 报告和 PPTX 都会用它；
`schemas/diagram-spec.schema.json` 里 `title` 是**明文列出的顶层属性**（`additionalProperties: true`）。
但 `compile_diagram_spec` 构造 spec 时根本不写这个键，调用方传了也被静默丢掉。
后果是**凡是走 dispatch 出来的图，报告里一律标成 "Diagram 1" / "Diagram 2"**，读者得自己猜哪张是哪张。

修后报告标题变成：

```
report h2: ['module structure of engines uir-java-python j2p',
            'control flow of translate() in j2p emit regex.py']
```

## A. 决定 1 · 只给导出端放宽标签白名单，Mermaid 一个字符不动

### A.1 放宽成什么规则，以及为什么是这个规则

导出端（`diagram_layout.sanitize_label`，喂 SVG / HTML / PPTX）的规则从
「`isalnum()` 或在 `" _-.,()"` 里」改成 **`str.isprintable()`**。
Mermaid 端（`domain._safe_mermaid_label`）**一个字符都没动**，逐字确认过。

选 `isprintable()` 不是图省事。**它砍掉的恰好是「转义救不了」的那一类**：

| Unicode 类 | 例子 | 为什么转义救不了 |
| --- | --- | --- |
| Cc 控制符 | `\x00`、`\x0b`、`\x1b` | C0 区在 XML 1.0 文本里**即使转义也非法** |
| Cf 格式符 | `U+202E` 双向覆盖、`U+200B` 零宽 | 转义之后照样反转/隐藏渲染文本，肉眼骗人 |
| Zs/Zl/Zp 异常空白 | `U+00A0`、`U+2028` | 两个不同标签看起来一模一样 |
| Cs 代理项 / Cn 未分配 | `U+FFFE` | 根本不是良构 XML 内容 |

而它放行的一切（含 `< > & " '`、`[]{}`、`=`、`*+`、CJK、emoji）**都会被
`escape_xml_text` 在出口处转义**。也就是说：放宽之后，**字符集不再是安全边界，转义才是**。
`diagram_svg.escape_xml_text` 的 docstring 原本写着「sanitize_label 已经把这些字符都去掉了，
所以改这里只可能是 no-op」——**这句话现在是假的，已经改掉**。
安全边界上留一条过期的注释比不留更坏。

### A.2 那条被拆掉的「两个 sanitizer 逐字节相同」测试，意图是怎么补回来的

Ethan 的要求是：**不能只是删掉了事**。原来那一条断言其实在干两件事——
① 把每一侧的规则各自钉死，② 抓住两侧悄悄分叉。**「相同」从来不是想要的性质，
它只是当年两边恰好相等时表达②最便宜的写法。** 所以现在用 **4 条断言**替代 1 条等式，
并且把原来那份语料（`SANITIZER_CORPUS`）原样留着继续跑：

| 新断言 | 钉住什么 |
| --- | --- |
| `test_the_mermaid_rule_is_pinned_to_its_own_character_set` | ①Mermaid 侧：扫遍 BMP，接受集必须恰好等于 `isalnum() ∪ " _-.,()"`，且 `< > & " ' [ ] { } = %` 一个都不在里面 |
| `test_the_export_rule_is_pinned_to_its_own_character_set` | ①导出侧：接受集必须恰好等于 `isprintable()` |
| `test_the_export_rule_is_a_superset_of_the_mermaid_rule` | ②**关系**：导出集 ⊇ Mermaid 集（Mermaid 被放宽 → 红；导出被收窄 → 红），并且两者**不得再次相等**（放宽被回退 → 红） |
| `test_neither_rule_keeps_a_character_that_escaping_cannot_make_safe` | 两侧共同下限：控制符/双向覆盖/零宽/异常空白/未分配一律丢弃 |

扫描口径是 **BMP 全量（0x0000–0xFFFF，去掉代理区）+ 3 个星文平面样本**，
不是挑几个字符意思一下。另外补了
`test_both_rules_still_bound_and_collapse_the_shared_corpus`（长度上限 160、换行折叠、
连续空格折叠、永不返回空串）和 `test_mermaid_still_dismantles_the_injection_corpus`
（原语料在 Mermaid 侧的输出逐字钉死）。

### A.3 新增的注入负向对照（用「放宽后新放行的字符」构造）

新语料 `INJECTION_LABEL = '</text></svg><script>alert(1)</script><svg x="&\'y\'"'`
**只由放宽之前会被删光的字符组成**。新测试类 `WidenedAllowlistInjectionTests` 断言两件事，
**分开断言，因为放宽之前只有第二件是真的**：

1. `test_the_payload_actually_reaches_the_renderer` —— 这串东西**原样通过了 sanitize**
   （`changed == False`）。**没有这一条，下面全部都是「因为字符被删掉了所以安全」的假绿。**
2. 它在 **SVG / HTML 报告 / PPTX 三处都是死的**：`&lt;script&gt;` 在、`<script` 不在、
   `</svg>` 恰好出现一次、`<text>` 与 `</text>` 配平；PPTX 里遍历**每一个 xml/rels 部件**
   确认没有 `<script` / `<svg`。
   最强的一条是用真解析器验的：`ElementTree.fromstring` 能解析产物，
   并且把整串 payload **原样当作文本节点**交回来，`script` 元素数量为 0。

**顺带修正一条既有测试的定性**：`test_injection_in_a_label_cannot_escape_the_svg`

现在它才真正在量转义。代码里写了注释说明这件事。

### B.2 修法：一个读法，三个调用点

`generate_document` 与 `analyze_impact` **确实是同根因**（都只读 `from`/`to`），一起修了。

### B.3 `analyze_impact` 这条为什么单独重

它不是打印错，**是答错还不报错**：`b` 变更、`a` import `b`，喂 canonical 边时它答

`test_both_spellings_of_the_same_graph_give_the_same_answer` 钉的就是这条性质：
**同一张图换个拼法不能换答案。**
