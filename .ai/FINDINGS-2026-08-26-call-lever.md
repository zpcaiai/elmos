# 最后一根杠杆的验证：`CALL:user-function` 实测 **0**，不是 +18

2026-08-26（同日，headroom 之后）。仪器：`.ai/measurement-2026-08-26/call_lever_verification.py`。
证据：`call-lever-crossunit.json`。语料与 08-21/08-26 完全相同（20 个真实 PyPI 项目，
583 文件 / 7.06 MB），数字可直接对比。

## 为什么必须验这一个

组合搜索把「跨单元调用」排成唯一剩下的基石：全部调用 = **+18**，
2 元最优 `CALL:user-function + TYPE:MISSING` = +44。
但那个 18 是**镜像推出来的**，和「11 个函数只差一个注解」属于同一类断言——
后者一验证就只剩 5 个，而且全部多解。

**要为它建一整套过程间纯度证明之前，先把这个数换成真分析器裁的。**

## 方法：不改引擎，用内联把问题变成分析器能裁的形式

如果一个候选唯一的障碍是「它调用了用户函数」，而那个被调方本身是单条
`return <表达式>`，那么把被调方的表达式代进调用点，就得到**当前分析器能直接判**的源码。
内联后返回 READY，才证明调用确实是唯一障碍——**由真分析器在真源码上判的，不是镜像投影的。**

这个办法还顺手逼出 +18 藏起来的那个问题：
**调用一个本身就出界的函数，并不会因为「允许调用」而变得可提升。**
内联后的形态会直接把被调方自己的拒绝码摆出来。

四种结局，只有第一种算收益：

```
VERIFIED_BY_INLINE    内联后真分析器返回 READY
BLOCKED_AFTER_INLINE  内联后真分析器仍然拒绝——拒绝码说明是被什么挡的
CALLEE_NOT_INLINABLE  被调方不是单返回表达式 / 带关键字实参 / 调用图有环
UNRESOLVED_CALL       调用目标根本不是用户函数（内建、方法、库导入）——不在这根杠杆范围内
```

跨模块也解析：`from .x import f` 与仓库内的绝对导入都会被追到文件，
再export 追一层。**`from typing import cast` 一律不追**——对用户自己单元的纯度证明，
对标准库什么都没说。

## 结果

```
1,469 个候选
    1  ALREADY_READY          （全语料唯一那个）
  130  NO_CALLS_AT_ALL        （压根没有调用，不是这根杠杆的事）
1,151  UNRESOLVED_CALL
  108  CALLEE_NOT_INLINABLE
   79  BLOCKED_AFTER_INLINE   ← 调用被完整消掉了，仍然被拒
    0  VERIFIED_BY_INLINE     ← **一个都没有**
```

79 个里一共内联掉 **124 个调用点，其中 28 个是跨模块的**（分布在 22 个函数）。
调用这堵墙被整个拆掉之后，它们死在哪：

```
PYTHON_PARAMETER_TYPE_REQUIRED   56
PYTHON_RETURN_TYPE_REQUIRED      13   ← 合计 69/79 = 87% 死在类型墙
PYTHON_UNSUPPORTED_EXPRESSION     9
PYTHON_UNSUPPORTED_STATEMENT      1
```

**又是两堵墙。** 拆掉调用墙，函数只是改成死在类型墙——而类型墙那条路
headroom 已经实测过：上界 12，验证兑现 5，且 5 个全部多解。

剩下 10 个非类型墙的里，**7 个死在 `UNSUPPORTED_EXPRESSION:Call`**——
**内联之后还剩着的调用**，也就是内建或方法调用。它们也不是这根杠杆能救的。

## 那 1,151 个 `UNRESOLVED_CALL` 到底是些什么

4,226 个未解析调用点，按被调方分类：

| 类别 | 数量 | 占比 |
|---|---|---|
| 属性/方法调用 `x.foo()` | 2,032 | 48.1% |
| 内建 `len` `isinstance` `range` `int` `print` … | 1,252 | 29.6% |
| 绝对导入 | 358 | 8.5% |
| 裸名但查不到（类名 / 局部 / 全局） | 355 | 8.4% |
| **相对导入（同包，真正的跨单元用户函数）** | **229** | **5.4%** |

前 15 个被调名：`len`(179) `isinstance`(137) `range`(102) `int`(68) `print`(53)
`ValueError`(45) `str`(39) `list`(37) `abs`(35) `getattr`(34) …

**「+18 全部调用」这个数里，压倒性多数是内建和方法调用**——恰恰是
「用户函数纯度证明」根本不覆盖的东西。真正属于这根杠杆的只有 5.4%。

## 决定性的那一条：这根杠杆是自指的

跨单元调用纯度证明能放行一个调用者，前提是**被调方本身可提升**（否则发射不出去）。
那么全语料有多少可提升的被调方？

**1 个。** `humanize-4.16.0/src/humanize/i18n.py::_gettext_noop`。

**而它有 0 个调用点。**（全语料以裸名 `_gettext_noop(` 调用它的地方：0 处 / 0 个文件。）

所以在今天这个子集宽度下，一套完整的过程间纯度证明**能授权的调用点数量是零**。
这根杠杆的价值不是 +18，是 **0 —— 而且要等到子集的其余部分先宽到让被调方可提升，
它才开始有价值**。先做它就是先建一座通向空地的桥。

## 这把尺子自己能不能给出非 READY（负控制）

不做变异测试的测量不算测量。合成语料两轮，8 个用例全部落在预期分类：

| 用例 | 期望 | 实得 |
|---|---|---|
| 调用纯单返回被调方 | VERIFIED | VERIFIED |
| 被调方体内是 `%`（引擎明确拒绝） | BLOCKED + 被调方自己的码 | BLOCKED `PYTHON_FLOORED_MODULO_OUTSIDE_CERTIFIED_SUBSET` |
| 调用内建 `len` | UNRESOLVED | UNRESOLVED |
| 被调方是多语句函数 | NOT_INLINABLE | NOT_INLINABLE `not-a-single-return-expression` |
| **跨模块**调用纯被调方 | VERIFIED | VERIFIED（cross=1） |
| 跨模块调用 `%` 被调方 | BLOCKED | BLOCKED |
| `from typing import cast` | UNRESOLVED | UNRESOLVED |
| 跨模块 + 别名再export | VERIFIED | **一开始是 UNRESOLVED —— 见下** |

**负控制抓到了我一个真 bug。** `from .reexport import triple as triple_again`：
本地绑定的是 `triple_again`，而目标模块里那个名字叫 `triple`。我的导入表只存了
本地名，拿本地名去目标模块里找当然找不到，于是**静默报成「未解析」**。
这类错只会让数字偏小，不会报错——**没有负控制就永远发现不了**。

语义等价另做求值对拍：`double(a) + 1` → `a * 2 + 1`；
优先级危险的 `add_one(a) * 3` → `(a + 1) * 3`（在 AST 上替换再整体 unparse，
括号由 unparse 负责，不是字符串拼接）；嵌套 `add_one(double(a)) - add_one(b)`
一次内联 3 个调用 → `a * 2 + 1 - (b + 1)`。三例在 4–7 组向量上逐一相等。

内联可能重复求值非平凡实参（参数用了两次而实参不是名字或字面量），
全语料只出现 **2 处**，且**逐条记在证据里**——在这个子集里观察不到差别，
但「观察不到」是关于子集的断言，不是关于内联的，所以记录而不是假设。

## 需要公开更正的数

**`CALL:user-function` / 全部调用 = +18 → 实测 0。**

这是本轮第六个被验证推翻的镜像投影（前五个：`list[str]` 13→0、body_clean 32→13、
类型面上界 31→12、calls_only 27→18、「只差一个注解」11→5）。
**镜像六次全部偏乐观，方向一次都没反过。**

## 结论

headroom 说 profile 天花板是 9.15%，类型面 ≈0，唯一剩下的基石是跨单元调用。
现在跨单元调用也验成了 0，而且是**结构性的 0**：它需要被调方先可提升。

**`typed-pure-function-v1` 这个 profile 上已经没有单点杠杆了。**
剩下的选择只有两个，都不是「再放宽一条规则」：

1. **换 profile**——4,128 个类方法（占全体 25.7%）整个在自由函数 profile 之外，
   这是最大的一块，但那是新 profile 不是放宽。
2. **同时拆两堵墙**——类型推断 + 调用纯度一起做。但 headroom 已经证明
   类型推断在最可能成功的 5 个点上答案都不唯一，`ir_local_bindings`
   拒绝推断的设计决定因此站得住。

**任何「只放宽一条规则」的提案，从今天起需要先给出内联验证或等价的真分析器证据。**
