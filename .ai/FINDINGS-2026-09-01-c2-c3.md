## 1. C2 为什么选自绘 SVG 而不是 Mermaid

Backlog 要求"二选一，先定一个"。定的是 **自绘 SVG**。四条理由，按分量排：

1. **C3 的验收把这件事决定了。** 验收是"图不是位图糊的（矢量嵌入）"。
   PPTX 里要矢量就得有几何：`prstGeom` / `custGeom` 要坐标。Mermaid 给的是文本，
   要坐标必须先经外部渲染器出 SVG 再转 DrawingML —— 两条管线、两套失真。
   自绘让**同一份整数几何**同时喂 SVG 和 DrawingML，图在报告里和在 PPT 里是同一张。
2. **确定性是按构造成立的，不是靠运气。** 布局全是 Python `int`，没有浮点、
   没有时钟、没有哈希序、没有字体度量。Mermaid 渲染器会生成内部 id / ARIA id，
   字节一致要额外后处理去保证。
3. **外部渲染器在这台机器上没装成。** 我真去试了（§4.5），`npx @mermaid-js/mermaid-cli`
   在 40 秒 shell 超时内没装完（要拉 Chromium）。这条记 **`NOT_PROBED`**，
   不是 `REJECTED`——我没有证明它不行，我只是没装上。
4. **引擎是零依赖的**（`pyproject.toml` `dependencies = []`）。
   引入 node + puppeteer 工具链等于给这个引擎加一条重依赖。

**既有的 Mermaid 渲染器一个字没动。** `elmos-diagram-rendering`
（`domain.render_diagram`）还是原样输出 `text/vnd.mermaid`，它的三键输出元组
`("content", "digest", "media_type")` 被资格契约钉死，本来也动不了。
两个渲染器共用同一个标签白名单，且**有测试把二者逐字节钉在一起**
（`test_sanitizer_is_byte_identical_to_the_mermaid_sanitizer`），防止将来分叉。

## 1.1 为什么导出在 CLI 而不在 Skill handler 里

这不是风格选择，是契约逼出来的。读了 `qualification_contract.py` 与 `runtime.py`：

## 3. 实现期抓到的真缺陷：有环 Spec 让所有图形跑到画布外

### 3.1 怎么发现的

不是读代码发现的。是把一个 32 节点、62 条边（含一条回边、一条自环）的 Spec
真渲染成 PPTX、再用 LibreOffice 转 PDF、再 `pdftotext` 抽文字时发现的：
**第 4 页只抽出 "Diagram 1"，32 个节点标签一个都没有。**

顺着查 slide XML：

```
$ unzip -p deck-big.pptx ppt/slides/slide4.xml | grep -o '<a:off x="[0-9]*" y="[0-9]*"' | head -1
<a:off x="5324166" y="30594500"
```

幻灯片高度是 `6858000` EMU。`y = 30594500` 是画布外四倍远的地方。

### 3.2 根因（两个，叠在一起才炸）

1. `_assign_layers` 在**所有**边上做最长路径松弛。图有环时每一轮松弛都能把环上的层号 +1，
   32 个节点跑满 32 轮 → 入口节点被推到 **layer 96**。
2. 画布高度用的是 `len(rows)`（**被占用的层数**），而节点 `y` 用的是
   `layer_index * (NODE_HEIGHT + VERTICAL_GAP)`（**原始层号**）。
   层号一旦稀疏（96、97、98 三层但 `len(rows)=3`），高度算出 328px，
   `y` 却算到 27000px 开外。SVG 里同样中招——图形全在 `viewBox` 外，渲染出来是空白。

### 3.3 修法

- 先用**迭代式**（非递归，避免深图爆栈）DFS 按 spec 顺序找出闭环边，
  松弛只在剩下的 DAG 上做；闭环边正好就是边路由本来要甩到侧边通道的那批。
- 再把层号**压实成稠密 rank**（`sorted(set(layer))` → 0..k-1），
  让"画布高度"和"节点 y"按定义一致，就算将来层号又出现空洞也不会再错位。

两条都写进了代码注释，注明是被什么打脸才加的。

## 一个环境事故（值得记，因为它不报错）

Ethan 第一次跑这三条命令时全部失败，原因不是代码：
**终端的 cwd 是一个被改过名的目录**（`elmos` → `elmos-deletion-residue-20260830-1818`，
08-30 18:18 的一次删除留下的）。shell 记的是 inode，`$PWD` 仍印着 `elmos`，
但相对路径解析走的是改名后的实体，于是 `open` / `python` / `make` 三条全落到残骸树上。

- `make` 的报错是 **`No rule to make target`** —— 看起来像 Makefile 坏了，实际是站错了树。
- `AIProjects/` 下现在有 **18 个 `elmos-*` 目录**（residue / recovery / recreated / closeout /
  delivery 快照），名字互相像，**站错树时命令不报错，只是行为不对**。
- 判据：**`pwd -P`**（走物理路径，不信 `$PWD`）。这是唯一可靠的自检，成本一条命令。

**教训与 §7 的路径更正是同一类**：交付给别人执行的命令，光验「文件在不在我这边」不够，
还要给出「他那边怎么确认自己站对了地方」。
