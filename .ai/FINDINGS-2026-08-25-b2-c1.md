## 2. 两个实现增量

### 2.1 `certified-drop-v1` —— `DROP TABLE [IF EXISTS] <name>`

每个修饰符都拒绝，且拒绝理由写成数据（`_DROP_TABLE_REFUSED_MODIFIERS`），
所以报错永远说得出具体分歧而不是一句 unsupported：

| 修饰符 | 分歧 |
| --- | --- |
| `CASCADE` | PG 连带删依赖对象；Oracle 是 `CASCADE CONSTRAINTS`（只管约束）；**MySQL 解析后忽略**；SQL Server 没有 |
| `RESTRICT` | PG 默认值；Oracle / SQL Server 都没有 |
| `TEMPORARY` / `PURGE` | 命名空间不同 / Oracle 回收站专有 |

多表 `DROP TABLE a, b` 也拒绝：PG 与 MySQL 里是**原子**的，Oracle 没有，拆开会改变部分失败后的残留。
`IF EXISTS` 的目标支持集刻意与 `CREATE TABLE` 相同（只有 PG + MySQL）：
SQL Server 2016 / Oracle 23ai 才有这个拼法，而**本引擎钉的是解析库版本，不是目标服务器版本**。

### 2.2 正则 CHECK —— 从「按算子拒绝」改成「按模式准入」

原先 `~` 与 `LIKE` 一并被整体拒绝。实测语料后改了：

```
8 个不同模式 / 418 次出现 / 全部落在可移植核心内
其中 400 次是同一个 ^[0-9a-f]{64}$（SHA-256 形状守卫）
```

新的三条保证，比原来的整体拒绝**更强**而不是更弱：

1. **模式闸门**：`\d \w \s \b`、`(?...)`、反向引用、`[[:alpha:]]`、`\p{L}` 一律拒绝
   （`CERTIFIED_DDL_UNSUPPORTED_CHECK_PATTERN`）——这些在 PG ARE / MySQL ICU / Oracle POSIX 三个引擎里含义不同。
2. **大小写敏感在发射端钉死**：PG 发 `h ~ '...'`（本就大小写敏感）；
   MySQL 与 Oracle 发 `REGEXP_LIKE(h, '...', 'c')`。
   **MySQL 的 REGEXP 跟随列排序规则**，8.0 默认 `utf8mb4_0900_ai_ci` 是大小写不敏感的，
   `^[0-9a-f]{64}$` 会连大写十六进制一起接受——约束会**悄悄变弱**，而且要等脏数据落库才看得见。
3. **SQL Server 失败关闭**（`CERTIFIED_DDL_REGEX_CHECK_UNREACHABLE_ON_TARGET`）：
   它没有任何正则谓词，降级成 LIKE 会接受另一个字符串集合（LIKE 没有有界量词、没有字符类）。

### 2.3 ⚠️ 实现期在自己的改动里抓到一个真缺陷

第一版**把 `REGEXP_LIKE(col, pat, 'i')` 的匹配参数整个丢掉了**，然后在发射端钉上 `'c'`。
后果是方向相反的同类事故：一个大小写**不**敏感的源，会变成目标端更严的约束，
**拒绝掉源库本来接受的行**。补了两道闸：

- `CERTIFIED_DDL_UNSUPPORTED_CHECK_MATCH_PARAMETER`：只认 `'c'`，其余（`i`/`m`/`x`/`n`）拒绝。
- `CERTIFIED_DDL_COLLATION_DEPENDENT_REGEX`：**MySQL 源且没写匹配参数时拒绝**——
  它的大小写敏感性来自列排序规则，而这条语句不携带排序规则，本引擎也没有目录可查。
  接受它就等于「猜一个源语义，再把这个猜测钉到目标上」。
  PG 的 `~` 恒敏感、Oracle 无参默认敏感，两者都可判定，照常接受。

## 3. 两次预估、两次错了 15 倍。这条比两个实现都重要

| 扩容 | 形状表说被阻塞 | 我的预估 | **实到** |
| --- | ---: | ---: | ---: |
| `DROP TABLE` | 80 | +80 | **+15** |
| 正则 CHECK | 389 | +389 | **+15** |
| 合计 | | +469 | **+30** |

两次都是同一个机制：**被阻塞的语句是多重阻塞的，拿掉一层只会露出下一层。**

- 80 条 `DROP TABLE` 里 **65 条表名是带引号的**（osticket 的 `"%TABLE_PREFIX%api_key"`，
  模板占位符，不是标识符）→ 转成 `CERTIFIED_DDL_QUOTED_IDENTIFIER`（72 → 137）。
- 439 条 CHECK 阻塞消掉 369 条之后，`CERTIFIED_DDL_UNSUPPORTED_TYPE` 从 **92 涨到 443**
  ——那 351 条语句既有正则 CHECK **又**有 JSONB 之类的列类型。

**所以 blocker 表不能当加法用。** `sum(blockers)` 远大于「被阻塞的语句数」，
因为同一条语句在多个码上各计一次（准确说：解析器快速失败，只记录**最外层**那个原因）。
`FINDINGS-2026-08-25-remaining-items.md` §4.1 里那张「每项值多少 pp」的表**据此作废**——
那些 pp 是上界，不是增量。

**给下一轮的规矩**：动手前先按 `(语句形状 × 内层原因)` 交叉统计，或者干脆
先做一个「收集全部违规而不是快速失败」的诊断模式。只看一层就报工期，会稳定地高估一个数量级。

## 4. 需要你复核：我推翻了一条既有决定

`models.CheckOperator` 原有注释明写：

> …which is why they need no per-dialect rendering while LIKE and regex (which do diverge) stay out.

并且 `test_check_predicates.py` 有一条参数化用例把「regex 必须被拒」钉住。**我把它拿掉了。**

我的理由：那条注释给的判据是「不需要逐方言渲染」，而本引擎**本来就有**逐方言渲染
（`render_type` / `render_reference_actions` 都是）。真正的风险是语义分歧，而分歧被三件事收住了：
模式核心闸门 + 发射端钉死大小写 + SQL Server 失败关闭。语料实测 8 个模式全在可移植核心内。

代价与残余风险，照实列：

- 这是**扩大了**引擎接受面的改动，且改动的是别人写下的、有测试锁住的决定。
- 收益的 95.7% 是**我们自己 schema 里的一个复制粘贴惯用法**（400/418 是同一个哈希守卫），
  对客户 schema 说明不了什么。
- 我把 `test_scan.py` 里那条「次数 vs 不同原因」的用例的**夹具**也换了
  （它原来正好用正则 CHECK 当「被阻塞的重复惯用法」，现在不再被阻塞了）。
  用例的**意图**保留，换成了 JSONB 列这个仍然被阻塞的重复惯用法，并在代码里写明了换的原因。
- 新增 `tests/test_regex_check_predicates.py`（22 条）承接原来那一行所承担的保证。

**如果你认为这条不该改，回滚点很干净**：把 `CheckOperator.MATCHES_REGEX` 从枚举里去掉，
`parser` 的 `exp.RegexpLike` 分支删掉，两条测试改回去即可；`certified-drop-v1` 不受影响。

# 附录 A（2026-08-26）：真库执行级证据 —— 找到 5 类语法腿看不见的缺陷

> Mac 已复验 `318 passed`。本附录是在此之上补的执行级证据，
> 服务器：**PostgreSQL 16.13** 与 **MySQL 8.0.46**（`@@collation_server = utf8mb4_0900_ai_ci`）。
> Oracle 与 SQL Server 没有免费 rootless 本地实例，保持 `EXECUTION_NOT_AVAILABLE`——**不是通过**。

## A.1 正则 CHECK：反事实成立，10/10

先验最要紧的那条——**如果朴素的 MySQL `REGEXP` 其实并不接受大写，那么钉 `'c'` 就是多余的，
接纳正则进子集的整个理由也就不成立**。真服务器上：

```
C1 naive REGEXP  / lowercase   ACCEPTED     <- 朴素发射
C1 naive REGEXP  / UPPERCASE   ACCEPTED     <- 约束确实被悄悄放宽了
C2 emitted 'c'   / UPPERCASE   REJECTED     <- 引擎的发射守住了
C3 source ~      / UPPERCASE   REJECTED     <- 源语义
```

`C1 && C2 && C3` 成立才叫「翻译保住了这条约束」。10/10 通过。
执行的 DDL 全部取自 `translate_ddl` 的输出，不是手写的。

## A.2 八个模式的跨引擎等价：35/35，零分歧

语料里出现过的 8 个正则模式，每个配一组跨越边界的探针（都含大小写翻转），
在 PostgreSQL 与 MySQL 上逐行比对接受/拒绝：**35 个探针全部一致，0 分歧**。

## A.3 两条新拒绝是否站得住：都用服务器行为证明，不靠论证

| 拒绝码 | 证明方式 | 结果 |
| --- | --- | --- |
| `CERTIFIED_DDL_COLLATION_DEPENDENT_REGEX` | **同一条语句**在两种排序规则下跑 | `ai_ci` → ACCEPTED，`as_cs` → REJECTED。语句本身不决定语义，拒绝成立 |
| `CERTIFIED_DDL_UNSUPPORTED_CHECK_MATCH_PARAMETER` | `'i'` 源 vs 朴素译成 `'c'` | 源 ACCEPTED、译文 REJECTED——会**拒掉源库本来接受的行**，拒绝成立 |

两条也都验证了引擎确实在拒（不只是"应该拒"）。

## A.4 整个已准入语料真跑一遍 —— 找到 5 类真缺陷

把 971 条已准入语句全部发射并**按迁移顺序真执行**。发现的都是 sqlglot 重解析看不见的：

| # | 错误 | 数量 | 性质 | 处理 |
| --- | --- | ---: | --- | --- |
| 1 | `REFERENCES customers ()` 空列表 | 21 | **明确缺陷**，任何服务器都不接受 | 已修：无列表时发 `REFERENCES t`（四方言都表示"目标主键"，是忠实而非猜测） |
| 2 | MySQL 1170 TEXT 列进键 | 186 | TEXT→`LONGTEXT` 属 BLOB/TEXT 族，MySQL 不带前缀长度不能索引 | `CREATE TABLE` 路径已失败关闭。**前缀索引是更弱的约束**（只比前 N 个字符，两个不同值可能撞 UNIQUE），选 N 是 profile 决定不是翻译 |
| 3 | MySQL 1101 TEXT 列带 DEFAULT | 8 | 同族限制 | `CREATE TABLE` 与 `ALTER ADD COLUMN` 两条路径都已失败关闭 |
| 4 | MySQL 1064 保留字标识符 | 7 | 语料里真有一列叫 `signal` | 已加 MySQL 8.0 的 **261 个保留字**闸门。**不加反引号**：本 profile 在入口拒绝带引号标识符，出口偷偷加引号会让引擎发出自己读不回来的形状 |
| 5 | 剩余 201 条（1170/1064/1068/1239） | 201 | **全部是 `ALTER TABLE ADD CONSTRAINT` 与 `CREATE INDEX`** | **不可修**：这两种语句不携带列类型，引擎读单条语句且无目录可查。与既有的 `ALTER COLUMN TYPE` 拒绝同一类 |

第 5 条是本轮最诚实的一条结论：**certified-ddl-v1 无法保证 MySQL 上 `CREATE INDEX` /
`ADD CONSTRAINT` 的可执行性**，除非将来做一个带目录（catalog-aware）的模式。

## A.6 我自己的两次量测失误（都产生过看起来合理的错数字）

1. **每条语句单独回滚**：迁移语料是**序列**，于是每条 `ALTER` 都报"表不存在"，
   整体报出一个假的 31%。改成按顺序应用并提交。
2. **多语句脚本**：`emit_alter_table` 对多动作 ALTER 会合法地发出
   `ALTER ...;\nALTER ...`，而驱动一次只执行一条。驱动的拒绝**长得和引擎语法错误一模一样**。

两次都差点被记成引擎缺陷。所以 `run_corpus_execution.py` 现在强制把拒绝分成
`MISSING_OBJECT`（覆盖率有洞导致的连锁）与 `EMISSION_DEFECT`（服务器拒了本引擎产的 SQL）两类，
并且 MySQL 1824「Failed to open the referenced table」属于**前者**——它读起来像缺陷，其实是同一个洞。
