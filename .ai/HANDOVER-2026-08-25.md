## 5. 两个 codex 分支

| 分支 | 领先 | 自身改动文件 | 分叉点 |
|---|---|---|---|
| `codex/multitenant-task-finops-runtime` | 2 commit | 264 | `467e25551` |
| `codex/multitenant-task-finops-skills` | 1 commit | 181 | `5b6cb5468` |

两个都从那个 4 万文件的巨型提交**之前**分出去，分叉比 perf 更深。

**时间**：各 1–2 天。

**方法（必须照做，这是这次会话最贵的教训）—— 差分验证法**：

```
# 1. 基线：合并前的 main 单独跑一遍
git archive HEAD engines/<x> | (cd /tmp/base && tar x)
pytest > /tmp/base.txt

# 2. 候选：合并后跑一遍
pytest > /tmp/merged.txt

# 3. 只看差值
comm -23 <(grep '^FAILED' /tmp/merged.txt | sort -u) \
         <(grep '^FAILED' /tmp/base.txt   | sort -u)   # 必须为空
```

**绝对数字毫无意义**（这次基线就有 1182 个失败，全是环境缺工具链）。
唯一有意义的是"合并引入了哪些新失败"。

**额外必查**：两边都改过、但**没有冲突标记**的文件。这次 20 个这样的文件里，
出了 7 处 main 测试体被静默顶掉、2 个 TypeScript 收尾符号丢失、1 处 `build_verification`
形状不匹配。检查方法：
```
comm -12 <(git diff --name-only $MB HEAD | sort) <(git diff --name-only $MB $BRANCH | sort)
```
逐个做函数级 / 测试体级比对，不能只看 `git status` 干净就放行。

## 7. 交接必读：这个仓库的四个坑

1. **自动合并会静默取错。** 没有冲突标记 ≠ 合并正确。这次抓到的全部是"语法干净、
   `git status` 一片祥和、要到调用时才炸"。
2. **校验器就是规范。** `routes/inventory.json` 那 199 个文件的刷新，每个值都来自
   `route_runtime_metadata` 或校验器自己比对的生成器。不要编版本号。
3. **环境硬限制**：Cowork 设备桥不能 `unlink`（git 一失败就留死锁）、`device_bash` 45 秒超时、
   Mac 的 Python 是 3.10 而引擎要 3.11+、`git status` 在这个 4 万文件的树上会超时、
   `next build` 需要网络（设备侧没有）。
4. **红灯要分类。** 环境红、既有红、本次引入的红 —— 三者的处理完全不同。混为一谈的人
   会去"修"那些本来就该红的。

## 8. 费用

AI 成本在这个量级上不是主要项。上述 2–4 周的工作，按这次会话的调用密度推算，
大致是**几百美元**量级（取决于模型档位与计费方式）。同样的活由熟悉此仓库的工程师做，
人力成本高一到两个数量级。

**所以决策点不在 AI 费用，在返工风险。** 具体的量化例子：`translationRunner.ts` 读的
`build_verification` 形状引擎从来没写过，**任何真实报告都会被 409 拒掉，控制台一个仓库翻译
都接不下来**。这个只看 diff 永远发现不了，是跑 `tsc --noEmit` + 真装依赖才暴露的。
发现它约 20 分钟；漏掉它，代价是一次线上事故。

**唯一值得强制的流程**：每次改动后做"改前基线 vs 改后"的差分验证（§5）。
省掉这一步省下的钱，会以返工的形式加倍还回来。
