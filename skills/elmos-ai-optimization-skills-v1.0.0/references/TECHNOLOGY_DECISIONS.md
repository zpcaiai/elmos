# 条件技术选型

| 技术 | 采用条件 | 不采用/暂缓 |
|---|---|---|
| LangChain | 实际减少模型/工具/检索适配重复工作 | 已有网关足够；不要给每次API调用强行套框架 |
| LangGraph | 多轮取证、分支、人工等待和恢复值得显式建模 | exact、一次解释、编译、DAP、600秒计时 |
| RAG | 有可检索且可授权/固定版本的证据 | 已知文件符号直接定位，无须Agent先搜索 |
| Elasticsearch | 全文+字段过滤+向量统一搜索需求与运维能力成立 | 小规模PG已足够、没有收益基准 |
| pgvector | 已有PG且资源/过滤/索引计划经实测可承担 | 影响OLTP或无法达到已批准SLO |
| 独立向量库 | 已测独立扩缩容/容量/隔离需求 | 仅因RAG流行就增加第二重复后端 |
| Dify | 可视化业务/客户DSL/生成目标有明确价值 | 核心Harness/资源租约/独立认证 |
| 多Agent | 有独立上下文、read/write-set及关键路径收益 | 固定角色轮流讨论、共享冲突写、无预算loop |

ADR应记录痛点、当前实现、alternatives、测试环境/数据/模型、质量/latency/cost、实际版本/许可、批准scope与回滚。
无实际数据保持candidate/deferred；不将所有技术的“可选”写成依赖DAG里的“必须”。
LangChain高层Agent可能已经基于LangGraph，应检查真实实现避免双层同类循环。Java控制面保持既有语言，可在隔离Worker中适配必要组件。
