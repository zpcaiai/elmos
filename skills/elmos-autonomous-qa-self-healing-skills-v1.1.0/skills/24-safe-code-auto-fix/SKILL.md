# Safe Code Auto-Fix

## 目标

在隔离工作树和沙箱中生成最小产品代码补丁，并通过分层验证决定接受、审批或回滚。

## 何时调用

当工作流进入 `24-safe-code-auto-fix` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 批准可执行的 RepairPlan
- 干净基线提交、仓库和语言适配器
- 编译、静态分析、测试和安全命令

## 输出契约

- Patch、diff、提交/工作树引用和生成说明
- 编译/静态检查/失败用例/回归结果
- 接受、等待审批或拒绝结论

## 执行步骤

1. 从干净基线创建隔离工作树和短生命周期分支。
2. 限制可写路径、网络、命令和资源。
3. 生成最小 diff；记录每个 hunk 对应的修复意图。
4. 运行格式化、编译、类型检查和静态分析。
5. 依次运行原失败用例、新回归、影响测试和全量 Required 测试。
6. 任一门禁失败则回滚该候选，保留证据并在预算内尝试下一候选。

## 不可违反的控制

- 禁止直接写主分支和生产。
- 禁止删除/禁用失败测试、弱化断言或硬编码测试特例。
- Fixer 无权修改策略、门禁、证据和审批配置。
- R3 不自动执行；R2 不自动合并。

## 完成判定

- 补丁仅包含与缺陷相关的最小变更。
- 所有验证阶段有证据和不可变结果。
- 失败候选不会污染后续候选环境。
- 自动接受只发生在策略允许且全门禁通过时。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## 项目产出要求（v1.1.0）

- 本技能产生或修改的测试源、配置、数据、基线、报告、补丁或证据必须登记到 `ProjectOutputManifest`。
- 测试相关文件必须通过 `37-test-source-materialization` 写入目标生态原生目录；只存在于临时上下文不算完成。
- 任何文件变化都要更新 SHA-256、需求/用例引用和谱系；未登记文件不得进入最终 Bundle。
