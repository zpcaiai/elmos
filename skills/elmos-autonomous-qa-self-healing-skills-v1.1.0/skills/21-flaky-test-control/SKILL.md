# Flaky Test Control

## 目标

识别测试波动的真实来源，防止自动重试掩盖产品或环境问题，并推动隔离和修复。

## 何时调用

当工作流进入 `21-flaky-test-control` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 首次执行失败及证据
- 有限重复运行、环境和时序差异
- 历史波动、代码变更和资源指标

## 输出契约

- 稳定失败、产品波动、测试波动或环境波动分类
- 最小波动条件、责任模块和隔离状态
- Flaky 率、趋势与修复任务

## 执行步骤

1. 保留首次失败，按策略进行少量重复以分类。
2. 比较输入、环境、时间、资源和依赖，寻找相关因素。
3. 用固定 seed、冻结时间、资源隔离和重复顺序复现。
4. 区分真实竞态/不稳定产品与脆弱测试。
5. 将 Confirmed Flaky Required 测试设为门禁失败。
6. 只有根因修复并经过稳定窗口后才能解除隔离。

## 不可违反的控制

- 不得把“重跑通过”改写为 PASSED。
- 不得无限重试。
- 隔离测试仍计入质量债务和发布策略。
- 测试 self-healing 不能修改业务断言。

## 完成判定

- 每个波动项有分类证据和责任人。
- Required Flaky 不会被绿灯掩盖。
- 历史 flaky 率可按测试/模块/环境查询。
- 解除隔离需连续稳定证据。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## v1.1.0 文件状态

- Flaky 结论回写对应测试文件的验证元数据和责任归属，但不得自动删除或禁用该文件。
- 稳定性修复生成新 Artifact 版本并保留首次失败证据。
