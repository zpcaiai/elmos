# Load, Stress, Spike & Soak Testing

## 目标

测定正常容量、极限拐点、突发恢复、长时间泄漏和横向扩展效果。

## 何时调用

当工作流进入 `14-load-stress-spike-soak-testing` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 性能基线、容量目标和扩缩容策略
- 流量增长曲线、突发模式和耐久时长
- 资源配额、故障/降级规则和监控

## 输出契约

- 负载、压力、突发、耐久、容量与扩展测试结果
- 最大稳定吞吐、崩溃点、恢复时间和瓶颈
- 内存/句柄/连接泄漏与资源回收诊断

## 执行步骤

1. Load：在目标流量运行并验证 SLO。
2. Stress：阶梯增加负载直到预算破坏，定位首个饱和资源。
3. Spike：快速升降流量，观察排队、限流、扩容和恢复。
4. Soak：长时间稳态运行，检测泄漏、累积延迟和后台任务堆积。
5. Capacity：在不同副本/资源下测量扩展效率和成本。
6. 停止负载后验证系统回到健康状态且数据一致。

## 不可违反的控制

- 压力测试只能在授权隔离环境执行。
- 不得仅以服务未崩溃定义成功。
- 自动扩缩容测试要记录扩容延迟和冷启动影响。
- 耐久测试中任何证据丢失都会使结论无效。

## 完成判定

- 明确给出目标容量、最大稳定容量和断裂点。
- 突发后恢复时间和数据完整性符合目标。
- 耐久测试无未解释内存/连接/句柄增长。
- 瓶颈定位到可行动组件而非泛化结论。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。
