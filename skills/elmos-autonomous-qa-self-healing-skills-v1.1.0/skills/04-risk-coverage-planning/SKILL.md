# Risk & Coverage Planning

## 目标

基于业务风险和系统结构决定测试类型、组合、优先级、环境、数据、并行策略与预算，保证覆盖完整且避免无控制的组合爆炸。

## 何时调用

当工作流进入 `04-risk-coverage-planning` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 追踪图与需求优先级
- 变更集、复杂度、历史缺陷、数据敏感度和外部依赖
- 支持矩阵、SLO、资源与 wall-clock 预算

## 输出契约

- TestPlan、覆盖矩阵和测试 profile
- 场景、角色、状态、数据、浏览器/设备、负载和故障注入矩阵
- 预计测试数量、资源需求、关键路径与初始 ETA

## 执行步骤

1. 计算需求和组件风险分数，P0/P1 默认最高保障。
2. 为每类需求选择正向、负向、边界、状态、权限、并发和恢复策略。
3. 通过 pairwise、约束求解和等价类降低无价值组合。
4. 定义 PR 增量、夜间全量和发布认证三层套件。
5. 为性能、压力、UI 和混沌测试分配独立环境与资源。
6. 检查每个 Required 节点是否具有至少一条可执行计划。

## 不可违反的控制

- 预算不足时不能静默删掉 Required 测试；必须报告并失败或拆分运行。
- 风险降低必须有明确依据，不能仅因测试昂贵。
- 任何 NOT_APPLICABLE 都要有规则和审批。
- 性能预算缺失时只可生成 provisional 预算并标记待确认。

## 完成判定

- P0/P1 可执行计划覆盖 100%。
- 计划中每个测试类型都有环境、数据、Oracle 与证据要求。
- 组合策略可解释且可重复生成。
- 计划给出机器执行 ETA 区间和置信度。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## v1.1.0 产出规划

- 测试计划同时规划目标框架、原生目录、测试 Target、Fixture/Mock/数据、Bundle 和重放入口。
- 将文件数量、构建时间、Bundle 大小和发布时间纳入资源预算。
