# Repair Planning

## 目标

在修改代码前生成最小、安全、可回滚的修复计划，并确定风险、审批和验证范围。

## 何时调用

当工作流进入 `23-repair-planning` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- Defect、根因候选、追踪图和代码上下文
- 自动修复策略、代码所有权和风险目录
- 失败测试、影响分析和预算

## 输出契约

- RepairPlan、候选改动、禁止改动和风险等级
- 失败用例、影响回归、安全/变异和全量回归计划
- 回滚方案、审批要求和最大尝试次数

## 执行步骤

1. 确认缺陷可复现且根因置信度达到策略阈值。
2. 提出一个或多个候选修复，优先局部、可逆和最小 diff。
3. 计算受影响需求、API、数据、事件和测试。
4. 按路径和语义将修复分类为 R0–R3。
5. 定义明确验证序列和失败回滚条件。
6. 高风险或不确定修复转为建议，不直接执行。

## 不可违反的控制

- 无可复现失败不得自动修复。
- 不得把改测试作为产品缺陷的默认修复。
- 修复计划不得修改质量门禁或策略。
- 跨模块大重构不应混入缺陷修复。

## 完成判定

- RepairPlan 通过 Schema。
- 候选改动与根因和需求有明确因果关系。
- 验证范围覆盖直接和传递影响。
- R2/R3 审批要求正确触发。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## v1.1.0 文件变更计划

- 修复计划分别列出产品文件、测试文件、配置和基线变更；测试变更默认需要更严格审计。
- 计划必须说明哪些 Artifact 被 supersede、如何重新物化及如何更新 Bundle。
