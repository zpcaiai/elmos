# Mutation, Property & Fuzz Testing

## 目标

通过变异、属性和模糊测试检验测试套件强度，探索有限示例之外的输入和行为。

## 何时调用

当工作流进入 `27-mutation-property-fuzz-testing` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 业务不变量、类型/Schema、纯函数和解析入口
- 现有测试、覆盖率和变异基线
- 输入语法、资源限制和崩溃判定

## 输出契约

- Mutation score、幸存变异和薄弱测试区域
- Property 测试与最小反例
- Fuzz corpus、崩溃/超时/资源异常样本

## 执行步骤

1. 从需求提炼不变量、单调性、可逆性、幂等和守恒性质。
2. 为适合模块生成属性测试和随机数据 shrinker。
3. 对解析器、协议、序列化和边界入口执行受限模糊。
4. 运行变异测试，识别未被断言杀死的语义变化。
5. 将反例最小化并转成永久回归测试。
6. 修复前后比较变异得分和幸存区域。

## 不可违反的控制

- Fuzz 必须有 CPU/内存/时间和文件系统配额。
- 不得对生产端点执行无界模糊。
- 覆盖率高不能替代变异强度。
- 变异得分阈值按模块风险设定，不能全局任意降低。

## 完成判定

- 关键纯逻辑和解析入口有属性/模糊覆盖。
- 发现的反例可稳定重放。
- 补丁不降低批准变异基线。
- 幸存关键变异形成明确测试增强任务。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## 项目产出要求（v1.1.0）

- 本技能产生或修改的测试源、配置、数据、基线、报告、补丁或证据必须登记到 `ProjectOutputManifest`。
- 测试相关文件必须通过 `37-test-source-materialization` 写入目标生态原生目录；只存在于临时上下文不算完成。
- 任何文件变化都要更新 SHA-256、需求/用例引用和谱系；未登记文件不得进入最终 Bundle。
