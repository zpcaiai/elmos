# Specification Normalization

## 目标

把自然语言需求和约束转换为结构化、可追踪、可测试的规格节点，并显式暴露冲突、歧义和不可测试陈述。

## 何时调用

当工作流进入 `02-spec-normalization` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- ProjectSnapshot 中的需求、约束、用户故事和验收标准
- API/数据/UI 规格与代码行为证据
- 组织质量规则和风险分级

## 输出契约

- REQ/CONSTRAINT/UXR/NFR/AC 节点
- 前置条件、后置条件、角色、数据分类和业务不变量
- 歧义、冲突、缺失验收标准与置信度

## 执行步骤

1. 按语义单元切分文档，生成稳定 requirement_id。
2. 归一化主体、动作、对象、条件、结果和异常路径。
3. 从上下文提取验收标准；无法推导时标记缺失而非臆造。
4. 识别数值、时间、权限、兼容性和性能约束。
5. 比较多来源陈述，输出冲突组与优先级依据。
6. 把可测试性不足的节点置为 ambiguous/blocked，阻止假覆盖。

## 不可违反的控制

- 不得把代码当前行为当作需求来源，除非明确标记为 legacy baseline。
- 不得用低置信度推断自动覆盖明确用户要求。
- 任何需求合并或拆分必须保留来源映射。
- 模糊词如“快速”“稳定”“友好”必须转成待量化 NFR。

## 完成判定

- 每个节点有来源、优先级、Required 标志和状态。
- P0/P1 需求具有明确验收条件或被阻塞。
- 冲突与歧义可通过 API 查询并进入报告。
- 规格版本变化可追踪到受影响测试。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。
