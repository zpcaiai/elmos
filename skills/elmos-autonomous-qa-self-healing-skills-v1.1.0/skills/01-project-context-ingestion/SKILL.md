# Project Context Ingestion

## 目标

将需求文档、项目约束、用户要求、代码、API/数据库/UI 设计、现有测试和运行配置固化为可复现的项目快照。

## 何时调用

当工作流进入 `01-project-context-ingestion` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 文档与文件 URI、Git 仓库和提交
- OpenAPI/GraphQL/Proto、DDL、消息 Schema、部署清单
- 现有测试、覆盖率、CI、SLO、浏览器/设备矩阵和安全策略

## 输出契约

- 内容寻址的 ProjectSnapshot
- 每个来源的解析状态、哈希、解析器版本和诊断
- 技术栈、模块、入口、构建命令和环境依赖清单

## 执行步骤

1. 发现所有声明输入与仓库中的隐式规格文件。
2. 在只读环境解析文本、结构和元数据；保留来源定位。
3. 计算内容哈希并去重，禁止同名不同内容被静默覆盖。
4. 探测语言、框架、构建系统、服务、数据库、消息和 UI 入口。
5. 验证必需输入完整性；对 partial/failed 来源建立阻塞项。
6. 冻结快照，后续测试与报告都引用同一 snapshot_id。

## 不可违反的控制

- 不得从未记录的本地状态读取隐式输入。
- 解析失败的 Required 来源必须阻止认证。
- 敏感文件只保存脱敏元数据或加密引用。
- 快照冻结后不可原地修改，只能创建新版本。

## 完成判定

- 相同输入和解析器版本产生相同快照哈希。
- 每条后续需求都能回链到来源文件和位置。
- 快照清单覆盖构建、运行、测试和部署所需入口。
- 输入变化可生成结构化 diff。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。
