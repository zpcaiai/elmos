# Functional Test Generation

## 目标

为业务功能生成正向、负向、边界、状态机、权限、幂等、并发和错误恢复测试，并输出可执行代码。

## 何时调用

当工作流进入 `06-functional-test-generation` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 功能需求、验收标准、业务规则和状态模型
- 代码接口、UI/API 入口与数据模型
- 角色、租户、异常和依赖约束

## 输出契约

- 功能测试 DSL 与框架专用测试代码
- 需求—用例矩阵、边界值表和状态转移覆盖
- 新增夹具、测试数据和 Oracle

## 执行步骤

1. 为每条业务规则生成 happy path 与至少一个失败路径。
2. 从数据类型、校验、枚举、范围、空值和时间规则生成边界。
3. 从状态模型生成合法/非法转移及重复操作。
4. 为角色、租户和所有权生成允许与拒绝对偶用例。
5. 为创建/支付/提交等副作用生成幂等、并发和重试测试。
6. 编译并在最小环境试运行，失败则修正生成产物而非跳过。

## 不可违反的控制

- 不得只覆盖当前实现可见分支，必须由规格驱动。
- 负向路径必须验证错误语义与无副作用。
- 时间和随机性必须可控制。
- 用例不得共享可变数据导致顺序依赖。

## 完成判定

- 每条 P0/P1 功能需求至少含正向、关键负向和边界覆盖。
- 生成测试能在目标框架中编译并运行。
- 测试失败时提供最小输入和完整证据。
- 状态、权限和幂等关键不变量被显式断言。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## 项目产出要求（v1.1.0）

- 本技能产生或修改的测试源、配置、数据、基线、报告、补丁或证据必须登记到 `ProjectOutputManifest`。
- 测试相关文件必须通过 `37-test-source-materialization` 写入目标生态原生目录；只存在于临时上下文不算完成。
- 任何文件变化都要更新 SHA-256、需求/用例引用和谱系；未登记文件不得进入最终 Bundle。
