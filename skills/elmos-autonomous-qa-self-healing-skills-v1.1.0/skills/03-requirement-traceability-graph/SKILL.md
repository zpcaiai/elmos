# Requirement Traceability Graph

## 目标

建立需求—功能—接口—页面—数据—事件—代码—测试—缺陷—补丁—证据的全链路图，作为覆盖、影响分析和认证的事实基础。

## 何时调用

当工作流进入 `03-requirement-traceability-graph` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 规范化规格节点
- 仓库符号、调用图、路由、Schema、DDL 和事件拓扑
- 测试、缺陷、补丁和证据对象

## 输出契约

- 版本化 TraceabilityGraph
- 覆盖缺口、孤儿测试、未映射代码风险和低置信度边
- 按需求/模块/版本查询的追踪链

## 执行步骤

1. 为规格、架构、代码和测试创建稳定节点。
2. 通过显式注解、Schema、调用关系和语义匹配建立候选边。
3. 为自动推断边记录置信度和证据，低置信度边不计入严格覆盖。
4. 计算 Required 节点的映射覆盖与可执行覆盖。
5. 在代码/需求变更时增量更新图并保留历史版本。
6. 向规划、修复、报告和门禁提供统一查询。

## 不可违反的控制

- 覆盖率只统计存在可执行测试且 Oracle 有效的 verifies 边。
- 不得删除历史图版本以掩盖覆盖下降。
- 人工确认边必须记录确认人和依据。
- 孤儿测试不能替代对需求的覆盖。

## 完成判定

- 任一 P0/P1 需求可在一次查询中找到实现、测试与证据。
- 未映射 Required 节点导致门禁失败。
- 代码变更可返回传递影响的需求和测试集合。
- 图数据可导出并通过 Schema 校验。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## v1.1.0 文件级追踪

- 图中增加 `TEST_FILE`、`OUTPUT_BUNDLE` 节点以及 `materialized_as`、`contains`、`supersedes` 边。
- Required 测试没有物化文件，或测试文件没有需求/风险依据时，追踪门禁失败。
