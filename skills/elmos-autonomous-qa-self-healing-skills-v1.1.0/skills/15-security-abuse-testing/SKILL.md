# Security & Abuse Testing

## 目标

验证身份、授权、输入、会话、租户隔离、秘密、依赖、配置和业务滥用边界。

## 何时调用

当工作流进入 `15-security-abuse-testing` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 安全需求、威胁模型、数据分类和信任边界
- API/UI/消息/数据库入口与角色模型
- 静态、依赖、动态扫描和测试账户

## 输出契约

- 安全测试、滥用场景和发现清单
- 可复现证据、影响、严重度和修复建议
- Critical/High 门禁结论与例外记录

## 执行步骤

1. 基于数据流和信任边界建立威胁场景。
2. 验证认证绕过、水平/垂直越权、跨租户访问和会话生命周期。
3. 测试输入注入、上传、反序列化、路径、请求伪造和资源滥用。
4. 检查秘密、日志、错误、缓存和客户端存储泄露。
5. 合并静态、依赖、动态和业务逻辑测试，去重并验证真阳性。
6. 对限流、验证码、风控和审计进行规避与恢复测试。

## 不可违反的控制

- 只在授权范围和隔离环境执行主动攻击。
- 不得在证据中保存明文秘密或个人数据。
- 扫描器结果未经复现不得自动定为产品缺陷。
- 安全修复默认至少 R2；核心安全域为 R3。

## 完成判定

- 未解决 Critical/High 为零。
- 关键授权规则有正反向和跨租户证据。
- 所有发现具有最小复现、影响和代码/配置定位。
- 例外有责任人、补偿措施和到期日。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## 项目产出要求（v1.1.0）

- 本技能产生或修改的测试源、配置、数据、基线、报告、补丁或证据必须登记到 `ProjectOutputManifest`。
- 测试相关文件必须通过 `37-test-source-materialization` 写入目标生态原生目录；只存在于临时上下文不算完成。
- 任何文件变化都要更新 SHA-256、需求/用例引用和谱系；未登记文件不得进入最终 Bundle。
