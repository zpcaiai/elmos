# Resilience, Chaos & Recovery Testing

## 目标

验证系统在依赖故障、超时、网络异常、资源耗尽和节点故障下的降级、恢复和数据完整性。

## 何时调用

当工作流进入 `16-resilience-chaos-recovery-testing` 对应阶段，或上游技能产物变化导致本阶段失效时调用。不得跳过依赖技能直接伪造输入。

## 输入契约

- 架构拓扑、依赖、SLO、RTO/RPO 和降级策略
- 故障注入权限、隔离环境和观测指标
- 幂等、重试、熔断、限流、补偿与备份规则

## 输出契约

- 故障实验、稳态假设和恢复报告
- RTO/RPO、错误预算、数据一致性和用户影响证据
- 未生效的熔断/重试/降级缺陷

## 执行步骤

1. 定义正常稳态和可测业务不变量。
2. 逐项注入延迟、断网、错误、进程/节点终止、磁盘/连接耗尽。
3. 验证超时、重试、熔断、隔离和回退不会形成放大效应。
4. 检查写操作的幂等、补偿、重复和半完成状态。
5. 恢复依赖后验证流量、队列、缓存和数据自动收敛。
6. 对备份恢复和灾难切换执行可回放演练。

## 不可违反的控制

- 实验必须有 blast radius、停止条件和自动回滚。
- 生产实验默认禁止，除非专门审批与安全护栏。
- 故障注入本身的资源和网络变化必须被记录。
- 恢复成功不能只看健康检查，还要验证业务数据。

## 完成判定

- 关键依赖失败有可预测降级。
- 恢复时间和数据损失符合目标。
- 重试不会造成请求风暴或重复副作用。
- 每个实验包含前置、注入、观察、停止和恢复证据。

## 失败处理

- 输入缺失或 Schema 不合法：标记 `BLOCKED`，保留诊断，不得猜测为成功。
- 可恢复基础设施失败：保存检查点并按受限策略重试。
- 产品或策略失败：生成结构化缺陷/门禁结果，不得通过跳过或弱化规则绕过。
- 所有失败均写入证据清单和审计事件。

## 项目产出要求（v1.1.0）

- 本技能产生或修改的测试源、配置、数据、基线、报告、补丁或证据必须登记到 `ProjectOutputManifest`。
- 测试相关文件必须通过 `37-test-source-materialization` 写入目标生态原生目录；只存在于临时上下文不算完成。
- 任何文件变化都要更新 SHA-256、需求/用例引用和谱系；未登记文件不得进入最终 Bundle。
