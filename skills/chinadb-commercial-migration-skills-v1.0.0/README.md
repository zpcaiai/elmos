# ChinaDB Commercial Migration Skills v1.0.0

A production-oriented Codex / Claude Code skills package for building a vendor-neutral database modernization platform targeting major Chinese databases while **excluding PolarDB / PolarDB-X and TDSQL**.

## Target databases

- DM8
- KingbaseES
- openGauss
- TiDB
- GBase 8s / 8c / 8a
- HighGo / HGDB
- OceanBase (Oracle-compatible and MySQL-compatible modes)
- GaussDB (Oracle-compatible and M-compatible modes)
- GoldenDB

## Commercial capability stack

1. Data movement: full load, incremental CDC, resume/retry, reconciliation, cutover
2. DDL automatic conversion
3. SQL automatic conversion
4. PL/SQL / T-SQL conversion and database-logic decomposition
5. Application code automatic refactoring
6. Behavioral equivalence verification
7. Performance equivalence verification
8. Guarded automatic repair
9. Production migration certification

## Architecture

The package deliberately avoids nine independent migration products. It specifies one shared platform:

`Source Adapters -> Semantic DB IR -> Rule/Mutation DSL -> Target Adapters -> Differential Runtime -> Repair Loop -> E1-E5 Certification`

This lets a new target database be added as a Target Adapter without rebuilding the full stack.

## Critical completion contract

**A SKILL.md file is an implementation specification, not proof that the feature exists.** A skill may be marked DONE only when all required repository code has landed and the skill's evidence artifacts have been generated by real builds/tests against the target repository. No checkbox, prose claim, generated mock report, or package validator can substitute for runtime evidence.

Minimum DONE requirements:

- implementation files exist in the actual product repository;
- unit + integration + differential tests execute successfully;
- required fixtures are non-trivial and include negative cases;
- evidence JSON conforms to the supplied schemas;
- no TODO/FIXME/stub/pass-through implementation remains in the completed scope;
- route-specific certification gates pass or an explicit signed waiver is recorded;
- production certification never relies only on static SQL conversion success.

## Recommended implementation order

Read `CODEX_EXECUTION_BATCHES.md`. Start with the shared IR/evidence contracts, then source adapters, conversion engines, target adapters, verification/repair, and finally production certification.

## Package contents

- `skills/`: implementation-driving skills
- `schemas/`: machine-readable contracts for manifests, evidence, repairs and certification
- `config/`: default configurable gates
- `templates/`: report and waiver templates
- `references/`: vendor capability baseline notes as of 2026-08-13
- `validators/validate_package.py`: validates the skill package structure only; it does **not** certify an implementation
- `MIGRATION_CAPABILITY_MATRIX.md`: target-specific conversion strategy
- `CODEX_EXECUTION_BATCHES.md`: coding batches with code paths, tests, evidence and DoD

## Source systems in scope

Tier 1: Oracle, SQL Server/T-SQL.

Tier 2: PostgreSQL, MySQL/MariaDB, DB2 LUW, Sybase ASE.

The source abstraction is intentionally extensible. Route quality is certified independently: supporting one route does not imply that every source-target pair is production-ready.
