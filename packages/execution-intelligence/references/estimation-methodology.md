# 估算方法

## 为什么不能用文件体积推 token 预算

静态扫描回答的是「把磁盘上的材料喂给模型**一次**要多少 token」。项目实际消耗还包括：

- 同一批文件在多轮迭代里被反复读取；
- 失败重试和返工；
- 子 Agent 扇出，每个都带自己的上下文；
- 工具结果、编译输出、测试日志回填进上下文。

这些倍数由任务 DAG 的 `token_profile` 和不确定性分布表达，不由文件大小表达。

## 五类互斥 token

`input`（未命中缓存）、`cached_input`（缓存命中读取）、`cache_write`（写入缓存）、
`output`（可见输出）、`reasoning_output`（推理输出）。

它们互不重叠，`total` 是它们的和。测试逐样本断言这一点。
把 `total` 再加回某个分类是最常见的重复计数错误。

## Monte Carlo

每次抽样：

1. 对每个任务按三角分布抽时长（乐观 / 最可能 / 悲观）；
2. 按 `rework_probability` 决定是否叠加返工倍率；
3. 按 `failure_probability` 决定是否叠加恢复时间；
4. 把任务按依赖关系调度到有效并行容量上，得到 wall-clock；
5. 独立地对 token 画像抽不确定性倍率，得到该次的 token 总量。

有效并行容量 = `workers × 可用率 × 并行效率 × 模型并发系数 × 代码冲突系数`，下限为 1。
`code_conflict_factor` 存在是因为多个 Agent 在同一棵树上写入会真实互相拖慢——把它设成 1.0
需要证据，不是默认。

## 分位数不可相加

任务级 P90 之和 ≠ 项目 P90。项目区间来自整体抽样。报告里明确写出这一点，
因为"把每个任务的 P90 加起来当项目 P90"是最常见的误用，结果必然过于悲观。

## 校准

`calibrate` 按 `task_type|complexity|model` 分组计算 `实际/预测` 倍率。
样本数少于 5 的分组标 `applicable=false`，回落全局倍率并保留更宽区间。
`apply-calibration` 把倍率写回任务 DAG，并在每个任务上留下 `calibration` 块，
让后来的人能一眼看出这是校准过的估计还是原始估计。
